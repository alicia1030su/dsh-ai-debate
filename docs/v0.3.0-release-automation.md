# v0.3.0 自动发布审计与 PR 拆分记录

> 这一轮的重点不是继续加功能，是把**发布阻断**拆清楚：哪些是 GitHub 真正强制的、
> 哪些是 AGENTS.md 约定的、哪些是任务书额外加的、哪些是真实人员才能给的。
> 四类混在一起时，一条「等批准」会把所有普通开发一起卡住。

---

## 一、四类条件，分开列

| 类别 | 谁定的 | 实际内容 | 本轮如何处理 |
| --- | --- | --- | --- |
| **GitHub 分支保护** | 仓库 ruleset `26259294` | 仅三项：`required_status_checks`（Node 22.18 / 24）、禁止删除分支、禁止强推。**没有 `required_pull_request_reviews`** | 每次合并前用 API 核实；实测 `mergeStateStatus` 与三项规则 |
| **AGENTS.md 约定** | 仓库维护者 | 敏感路径改动需维护者明确授权；合并用 squash；不移动已发布标签 | 敏感改动一律停在 PR，不自动合并 |
| **任务书额外限制** | 历次任务书 | 例如「必须由 PR 作者提交 GitHub Approve Review」 | **这条不成立**：GitHub 不要求 review，且本仓库只有一个维护者（作者本人无法 approve 自己的 PR）。按维护者书面指令 + 精确 SHA 记录授权即可 |
| **真实人员验收** | 任务书 §六.11/12 | 真实用户试用、人工语义评分 | 0 人，**没有任何自动化能替代** |

**关键结论**：GitHub 不强制 PR review。前几轮把「等 Approve Review」当成硬门槛，
凭空给自动发布加了一道谁也无法满足的关卡 —— 而维护者的书面授权（关联 PR + SHA + 路径）
本来就是 AGENTS.md 认可的形式。

## 二、`ship.mjs` 审计：已实现与真实缺陷

### 已实现（直接复用，不重写）

| 能力 | 实现位置 | 实测 |
| --- | --- | --- |
| 自动区分普通 / 敏感 PR | `classifySensitive`（`ship-core.mjs`） | 本轮 4 个 PR 逐个判定，产品 PR 判 `false`、归档与工作流判 `true` |
| 普通 PR 全流程自动发布 | `preflight → … → verify_release` | 阶段齐全，含 tag/release/附件核验 |
| 敏感 PR 停在审核点 | `decideStage('pull_request')` → `block` | 有明确 reason 与 recovery |
| `--resume` 续跑 | `reached(stage)` + 状态文件 | 跳过已完成阶段，重算产物哈希 |
| 失败后按阶段恢复 | `RECOVERY[stage]` 全覆盖表 | 每个阶段都有恢复建议 |
| 不重复创建 Release | `decideRelease` | 附件名+字节数一致 → `reuse`；不一致 → `refuse` |
| 不移动已发布标签 | `decideTag` | 标签指向别处 → `refuse`，提示改用新版本号 |
| 网络失败不误报成功 | `waitForRelease` 按标签过滤失败运行 | 只认本标签的失败，不会把历史失败当成本次 |
| 不开 `--admin` | `enableAutoMerge` 用 `--auto` | 不绕过检查 |

### 真实缺陷（已登记 issue #32，未擅自修）

`ship.mjs` 在 `pr.state === 'MERGED'` 时直接当作「人工授权完成」：

```js
if (pr.state === 'MERGED') {
  // 走到这里说明上一轮停在了 PR，而人是手动合并的 —— 那次合并就是授权。
  log(`PR #${pr.number} 已被合并（人工授权完成），跳过自动合并与等待检查`)
```

**它不校验合并进去的提交，是不是被拦住时那个被审阅的提交。**

失败路径：授权 `A` → 之后又推了 `B` → 合并的是 `B` → `--resume` 认为「合并即授权」→
发布 `B`。**对 A 的批准被用来发布 B。**

为什么本轮不修：`scripts/ship.mjs` 与 `ship-core.mjs` 自身命中 `ship-logic` 敏感规则，
改它们需要维护者单独审核。修法与回归测试写在 issue #32 里。

### 另一处已登记（issue #31）

v0.3.0 把扫描核心判定抽到 `scripts/lib/zip-index.mjs`，但 `scan-rules` 的判据仍是精确文件
列表（只认 `audit-leaks.mjs` 与 `scan-archive.mjs`）。实测：

```
classifySensitive([{ path: 'scripts/lib/zip-index.mjs', status: 'A' }]).sensitive === false
```

即：改这个新文件可以改变「什么算违规」，却不触发敏感闸门。规则搬家后判据没跟着搬。

## 三、PR 拆分结果

原先 PR #30 把 27 个文件混在一起，其中 6 个是 `scan-rules` 敏感。结果是：只要敏感部分
没批，普通产品改动也进不去。按维护者要求拆分：

| PR | 内容 | 文件数 | 敏感 | 状态 |
| --- | --- | --- | --- | --- |
| **#33** | v0.3.0 产品化：版本、案例集 30 条、候选构建、文档 | 18 | 否 | **已合并** → main `2fb12a8` |
| **#36** | 四项故障注入测试 | 1 | 否 | **已合并** → main `0d66c1d` |
| **#37** | 预发布版本工具层（`parseVersion` / `isPrerelease`） | 5 | 否 | **已合并** → main `6c5dfe7` |
| **#35** | 归档完整性修复（issue #29） | 6 | **是**（`scan-rules`） | **OPEN**，CI 双绿，等审核 |
| **#38** | 发布工作流支持预发布（`--prerelease`） | 2 | **是**（`workflow`） | **OPEN**，CI 双绿，等审核 |
| #30 | 原混合 PR | 27 | 是 | 已关闭，被上面四个取代 |

### 拆分时踩到的两个真实坑

1. **squash 之后 diff 会变宽**：归档分支原本基于 squash 之前的 `53f5e81`，开 PR 后显示
   24 个文件（把已合并的产品文件又算了一遍）。修法是以**已合并的 main 为父提交**重建
   commit（tree 相同），diff 才收到 6 个。第一次重建的 PR #34 因此关闭重来。
2. **`push-via-api.mjs` 按 tree 判「已推过」**：合并提交这类「内容相同但祖先不同」的情形
   会被判成「已经一致」而跳过。需要用 `git/commits` API 显式建以 main 为父的提交。

## 四、预发布版本支持（#37 + #38）

`0.3.0-rc.1` 之前发不出去的两处原因，分开修：

| 层 | 改动 | PR | 敏感 |
| --- | --- | --- | --- |
| 版本工具 | `parseVersion` / `isPrerelease`；README 四种上下文的 POST/GET 正则接受 `-rc.N`；`version.mjs check` 在预发布时**要求**工作流里有 `--prerelease` | #37 | 否 |
| 发布工作流 | 三态判定：预发布 / 正式 / **不合法**；`gh release create` 带 `$PRERELEASE_FLAG` | #38 | **是** |

设计要点：

- **三态而不是两态**：`0.3`、`0.3.0.1` 必须被拒绝。两态写法会把它们归进「正式版」，
  然后以 Latest 的身份发出去 —— 一个拼错的版本号变成一次公开的正式发布。
- **断言与改动同进同出**：#38 里那条测试检查「标志变量**真的出现在命令行里**」。
  变异验证：把 `$PRERELEASE_FLAG` 从命令行删掉但保留变量计算 → 测试立刻变红。
- **`ci-guard` 拦下了一次真实退化**：第一版用 `printf | grep`，被 CI 守卫判为
  「有管道但没 pipefail」。改成 bash 内建 `[[ =~ ]]` 后通过。

**当前状态**：`version.mjs check` 在预发布版本上会**有意失败**，因为工作流那半边还没合并。
这是想要的：宁可发不出去，也不要发一个被标成 Latest 的候选版。

## 五、故障注入（#36）

补上任务书 §7.2 里一直没有自动化证据的四类，加一条回滚：

| 场景 | 断言 |
| --- | --- |
| 写盘中途被杀 | `state.json.tmp` 不影响正式文件；正式文件逐字节不变 |
| 未完成的模型生成 | 候选缺 `targetSnapshot` 时整份 store 仍可读；该候选不得是已批准 |
| 配置解析失败 | 坏人格落默认、非数字落默认；非对象输入不抛 |
| 会话部分损坏 | 要么整份拒绝并给原因，要么好会话仍读得出 |
| 升级后回滚 | 旧文件逐字节恢复，旧会话仍可读 |

写这些时发现两处与直觉不符的真实行为，**按实际契约断言而不是放宽**：

1. `resolveConfig` 的 `readNumber` 只挡非有限数，**不做区间收敛**（`intensity: 999` 会原样
   保留，区间在 schema 层）。测试钉的是当前行为，并在注释里写明「这不是理想行为」。
2. store 的 `usage` 是数组不是对象，写成对象会在 `slice` 处直接抛 `write_failed`。

## 七、P0 收口：敏感覆盖与授权绑定（issue #31 / #32）

### #31：判定搬家之后，敏感名单要跟着走

`classifySensitive` 原来只认 `scripts/audit-leaks.mjs` 与 `scripts/scan-archive.mjs`。
v0.3.0 把判定抽进 `scripts/lib/`，于是改 `zip-index.mjs`（索引自洽、路径穿越、预算）、
`scan-finding.mjs`（命中记录能带出什么）、`fixture-allowlist.mjs`（哪些假值可以放过）
都不会停 —— 门禁挡的是文件名，不是风险。

修法是**显式清单 + 导入闭包断言**：

| 规则 | 覆盖 |
| --- | --- |
| `scan-rules` | 两个入口 + `zip-index` / `scan-finding` / `fixture-allowlist` |
| `pack-rules` | 三个打包入口 + `git-objects.mjs`（决定从哪个提交读哪些 blob） |
| `ship-logic` | `ship.mjs` / `ship-core` / `delivery-status` / `ship-review` |
| `release-versioning` | `version.mjs` / `version-core.mjs`（rc 会不会被标成 Latest） |
| `verification-rules` | `archive-verify` / `verify-source-archive` / `verify-install` / `deps` / `import-scan` / `ci-guard` |
| `release-notes` | `release-dry-run` / `release-notes`（附件哈希与安装命令） |

测试里有一条**导入闭包**断言：从敏感入口解析真实 `import`，闭包里每个本地模块都必须被
某条规则命中。将来再拆一个 `scripts/lib/zip-budget.mjs` 而忘了登记，CI 直接变红，
不需要等下一次「改了没事」的事故。

没有为了减少阻断而放宽任何规则；新增的四条规则只收紧。

### #32：授权必须绑定最终代码

旧代码在 `pr.state === 'MERGED'` 时直接把合并当授权。失败路径：

1. 停在审核点，维护者看到 head `A` 并批准 `A`；
2. 批准之后又推了 `B`；
3. 合并的是 `B`；
4. `--resume` 看到 MERGED，打标签发 `B`。

现在的判定链（`scripts/lib/ship-review.mjs` + `ship-core.judgeMergeGate`）：

| 检查 | 依据 |
| --- | --- |
| 审核锚点存在 | 停下时写进 `.ship/state.json` 的 `github.review`：head、tree、每个改动路径的 blob |
| 真实授权 | GitHub PR review，作者是仓库维护者，正文是 `ship-approval: v1` 模板 |
| 绑定 PR / HEAD / 范围 | review 的 `commit_id` 必须等于评论里的 head，也必须等于审核锚点；`scope` 覆盖全部敏感路径 |
| 合并内容一致 | 合并提交相对第一个父的逐路径 blob = 审核锚点的 blob；不要求合并 SHA 等于 head（squash 必然不同） |
| 新提交使授权失效 | PR 最终 `headRefOid` 不等于审核锚点即拒绝 |
| 授权早于合并 | `submitted_at` 晚于 `merged_at` 视为事后追认，拒绝 |
| 标签对应审核内容 | 打标签前再比一次 main 上的 blob；合并提交必须是 main 的祖先 |

行为回归（`test/v0300-ship-authorization.test.ts`，29 条）：

- 审核 A → 推 B → 合并 B → 拒绝；
- 正常授权 A → 合并 A → 允许（squash 新提交也允许）；
- 基线前进、被审核文件内容不变 → 允许；
- 授权范围漏路径、授权属于别的 PR、授权晚于合并、合并多带敏感路径 → 全部拒绝。

**授权 review 只能由维护者提交。** 流水线里没有任何创建 review 的函数；本文件描述的
格式不是让 agent 自己填 —— agent 填出来的只是它自己的意见，不是维护者的批准。

**当前状态**：修复本身在 `release/v0.3.0-ship-authorization` 分支，属于 `ship-logic`，
必须停在维护者审核点。未合并前，main 上的 `ship.mjs` 仍是旧行为，因此本轮不发布。
