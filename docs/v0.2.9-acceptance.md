## 二、跨进程锁回收的竞争窗口

### 缺陷分析（任务书要求的一节）

旧流程：读锁体 → 判断死进程 → `rename` 挪走 → 读取 graveyard 比对字节。

任务书列出的五步时序，逐步对应到代码：

| 任务书步骤 | 代码里的位置 | 是否成立 |
| --- | --- | --- |
| 1. 读取旧锁后，另一个进程替换锁 | `observed = await readFile(lockPath)` 之后 | 能 |
| 2. 回收进程把新锁移动走 | `await rename(lockPath, graveyard)` | 能——它移的是**当前**路径上的文件 |
| 3. 新进程趁路径空闲再次获取锁 | rename 之后 `lockPath` 为空，`open('wx')` 成功 | **能，这是关键** |
| 4. 回收进程恢复原锁失败 | `link(graveyard, lockPath)` 因路径已占而失败 | 能 |
| 5. 原持有者仍在写入 | 回收者被自己的调用方认为「已回收」 | **能** |

**结论：这个时序确实可能导致多个写入者同时进入临界区。** 根因不是「rename 不原子」
（它是原子的），而是**rename 把路径清空了**——空路径在 `wx` 语义下就是一张请柬。
字节比对救不了，因为它验证的是「回收者挪走了什么」，而不是「回收者现在持有什么」。

### 第一次复现尝试（失败，记录下来）

我最初写的是「起一个子进程轮询锁路径、回收者回收」的版本，输出是：

```
peer: PEER-ACQUIRED
store: RESOLVED
```

看起来像复现，但**不能作为证据**：对手可能是在 store 写完之后才拿到锁，那是完全合法
的时序。概率测试对这类缺陷无效——抓到一次不说明有，没抓到也不说明没有。

### 真正的复现（确定性注入）

`store.transact(decide)` 的 `decide` 回调在「已持锁、已读完、还没写」的位置执行。
在回调里替换锁文件，就精确复现了「读完之后锁被接管」这一刻，**零时序依赖**：

```
transact: threw write_failed
mutate:   threw write_failed
```

退回 v0.2.8 写法（去掉 `verify()`）后，同样的测试：

```
transact: RESOLVED（不该）
mutate:   RESOLVED（不该）
```

### 修复

两条互补，缺一不可：

1. **回收不是认领。** `breakStaleLock()` 只负责让出路径，回收者必须随后自己赢下
   `open('wx')` 才算持锁。输给对手就继续重试。
2. **写入前复核所有权。** 新增 `LockHandle.verify()`，在 `persist()` 之前重读锁文件
   比对 token。持锁与写入之间隔着若干 `await`，那正是被回收的窗口。

死进程留下的锁仍然可回收（基线测试守住：否则崩一次就永久卡死）。

### 验证

| 测试 | 检查什么 | 结果 |
| --- | --- | --- |
| 写入前锁被接管 → `transact` | 拒绝写入、磁盘原样 | 通过 |
| 写入前锁被接管 → `mutate` | 同上 | 通过 |
| 事务期间锁文件存在 | 临界区确实有保护 | 通过 |
| 死锁可回收 | 崩溃不会永久卡死 | 通过 |
| 活锁不回收 | v0.2.8 回归保持 | 通过 |
| 三方竞争 | 文档始终是合法 JSON，不出现半写 | 通过 |

**结论：任务书列出的五步时序已被消除——具体地说，「回收者自以为持锁」这条路径不再
存在，因为持锁现在必须在写入前被重新证明。**

**但这不等于锁是正确的分布式协议。** 没有租约、没有 fencing token、没有时钟假设；
如果宿主文件系统不保证 rename 的原子可见性，仍可能出问题。这条已写进 README 第 24 条。

## 六、设计取舍

**为什么列表要用发表路径的同一个函数，而不是再写一份比较。**
两份比较迟早会分叉，而分叉的方向无法预测：列表更宽 → 主人看到「已批准」但发不出去；
列表更严 → 已授权的候选反复要求批准。用同一个 `checkApproval()` 把两者绑在一起，
以后任何一边改动都会同时作用于另一边。

**为什么回收失败要拒绝写入而不是等一会儿再试。**
等待假设「对手会很快结束」，而这个假设在一次真实的锁竞争里没有任何依据。拒绝写入是
有明确后果的：调用方看到 `write_failed` 和一句可操作的话，重试即可。写入而丢失记录
是不可逆的。

**为什么预期快照构造不出来时仍然列出候选。**
没有指纹或没有绑定账号时，不存在可比较的绑定。此时藏起来会让主人以为「没有待办」，
而真相是「这条需要修配置」。列出来并写明「无法批准」是唯一的诚实选项。

**为什么没有把 `verify()` 做成可选优化。**
它每次写入多一次 `readFile`。这是一个很小的、局部的读，换来的是一条明确的安全属性：
写入时确实持有锁。把它做成可开关，等于把这条属性变成配置项，而没有人会在出问题前
主动打开它。
