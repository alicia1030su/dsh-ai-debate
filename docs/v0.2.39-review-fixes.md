## 一、源码包：发布模式必须 fail-closed

### 1.1 原来的行为

```js
function resolveCommit(rev) {
  try { return execFileSync('git', ['rev-parse', '--verify', `${rev}^{commit}`], …).trim() }
  catch { return null }          // ← 三种情况共用同一个 null
}
const commit = resolveCommit(requestedRev)
```

`null` 同时表示三件事：

1. 这里没有 Git；
2. `git` 二进制不存在；
3. **这个 rev 解析不了**（标签还没打、手滑、浅克隆）。

第 3 种落进了「没有 Git」的分支，于是脚本回落到工作树，打出一个**看起来正常、但不属于任何
提交**的包。发布者以为打的是 `v0.2.39` 标签，实际打的是磁盘上恰好存在的那堆文件。整段输出里
只有一行容易被忽略的 `working-tree`。

同一个 `argValue` 还让 `--rev`（不带值）变成 `''`，再变成 `HEAD` —— 一个什么都没指定的请求，
产出了一个确定的东西。

### 1.2 现在的行为

| 目录 | `--rev` | `--allow-working-tree` | 结果 |
| --- | --- | --- | --- |
| Git 工作树 | 不传 | 不传 | 打 `HEAD` |
| Git 工作树 | 有效 | 不传 | 打该提交 |
| Git 工作树 | 无效 / 空 | 任意 | **退出 2，不写文件** |
| Git 工作树 | 任意 | 传了 | **退出 2**（两种请求不能同时满足） |
| 无 Git | 不传 | 不传 | **退出 2，并提示两个选项** |
| 无 Git | 不传 | 传了 | 打工作树，输出标注「不能从提交复现」 |
| 无 Git | 传了 | 任意 | **退出 2**（指定了提交就不能拿磁盘顶替） |
| 仓库无提交（HEAD 未出生） | 不传 | 不传 | **退出 2** |

判定拆成两个函数：`insideGitWorkTree()` 回答「有没有 Git」，`resolveCommit()` 回答「这个 rev
是不是一个提交」。前者为真而后者为假时，唯一的处置是失败。

`--allow-working-tree` 是**显式的本地非发布模式**，只用于安全测试夹具与「从拷贝出来的目录看
一眼」，不能与 `--rev` 同时使用，在 Git 工作树里也不适用。

### 1.3 调用点

| 调用点 | 是否传本地开关 | 结论 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | 否 | 发布模式 |
| `.github/workflows/release.yml` | 否 | 发布模式 |
| `scripts/ship.mjs` | 否 | 发布模式 |
| `test/v0215`、`v0217`、`v0239` 的夹具 | 是 | 本地模式（没有 Git 的临时目录） |

`scripts/ci-guard.mjs` 增加反向检查：两个工作流只要出现 `--allow-working-tree` 就失败；
打包器必须仍然保有 `insideGitWorkTree` 的判断，防止整段被回退。

### 1.4 证据

`test/v0239-publish-gate.test.ts`（12 条）。整改前的红基线：

```
not ok 1  --rev 解析不到提交时必须失败，不能回退工作树
not ok 2  --rev 后面没有值时也必须失败
not ok 3  没有 Git 时默认拒绝，必须显式选择本地模式
not ok 5  本地模式不能替代一个指定不了的 rev
not ok 6  仓库还没有提交时失败，而不是打当前目录
```

整改后 12/12 通过。通过的两条在整改前也通过（`--allow-working-tree` 是新增开关、真实仓库
本来就能打包），所以红基线是 10 red / 2 green。

既有测试的调整只有一处：`v0215`、`v0217`、`v0239` 在无 Git 的夹具里显式传
`--allow-working-tree`。**断言没有改**；「不传就必须失败」由新测试单独覆盖，所以这是收紧，
不是放宽。

## 二、凭据扫描：从「目录名」改成「确切字节」

### 2.1 原来的实现

三层豁免叠在一起：

```js
const SCAN_EXEMPT = new Set(['src/security/output-guard.ts', 'test/v0214-…', 'scripts/source-zip.mjs'])
const FIXTURE_MARKER = /(?:fixture|dummy|example|fake|placeholder|test-only|FIXTURE)/i
…
if (SCAN_EXEMPT.has(rel)) continue
if (FIXTURE_MARKER.test(line)) continue
if (rel.startsWith('test/') || rel.startsWith('docs/')) continue
```

后果可以直接演示：把一把真的 AWS key 粘进 `test/anything.test.ts`，构建仍然是绿的；
在 `src/` 里写 `// example: <真钥匙>`，同样绿。`scripts/scan-archive.mjs`（独立扫描器）
有同一行 `startsWith('test/')`，所以第二个意见也同意。

### 2.2 现在的实现

只有一个判据：`(路径, 确切字面量)` 相等。

```js
if (isRegisteredFakeLiteral(rel, match[0], line)) continue
```

登记表在 `scripts/lib/fixture-allowlist.mjs`，共 7 条、分布在 5 个文件。下面只描述形状，
**不在这里写出完整字面量** —— 本文档自己也会进源码包、也会被同一个扫描器读；写出整串会让
文档成为新的命中项，只能再给文档开一条豁免，那又把「例外可枚举」这件事稀释了。要看确切字节，
看登记表本身（它把字面量拆成几段存放，理由见下）。

| 路径 | 允许的字面量（形状） | 为什么是假数据 |
| --- | --- | --- |
| `docs/v0.2.17-acceptance.md` | AWS 文档示例访问键（`AKIA…EXAMPLE` 形状） | 出现在「夹具标记会被绕过」的说明文字里 |
| `test/security/security-events.test.ts` | 占位 JWT（`Bearer …payload.sig`） | 中间段就是 payload/sig 两个字面词 |
| 同上 | mem0 形状的脱敏测试输入 | 用于断言事件记录里不会出现原值 |
| `test/v0211-weibo-cli.test.ts` | 占位 JWT（尾段为字母表顺序 `abcdefghij`） | 不是随机密钥 |
| `test/v0215-source-zip-security.test.ts` | 整行私钥常量（正文含 `FAKE`） | 只存在于隔离临时目录的构造代码里 |
| 同上 | GitHub 令牌形状的反例值（含 `MustFailBadly`） | 专门用来证明「不带标记的真凭据会被拦住」 |
| `test/v0217-exception-paths.test.ts` | AWS 形状的反例键 | 写进隔离临时仓库、用于证明扫描会失败 |

两个细节：

- **私钥登记整行，不只登记头。** 只登记 `-----BEGIN … PRIVATE KEY-----` 这一行的话，它在
  真钥匙里长得一模一样，等于给所有真私钥开了一个口子。整行登记之后，真钥匙粘进来那一行不同，
  仍然失败。
- **登记表里的字面量被拆成几段再 `join`。** 这份文件自己也会进包、也会被扫描；写整串会让它
  命中自己，于是只能再给自己开一条「整文件豁免」—— 正是本案要消灭的东西。拆点落在不构成
  模式的字符边界上，不是加密。

`scripts/scan-archive.mjs` 采用同一份数据、但保留自己独立的模式表与判定流程；一个扫描器
漏掉的形状，另一个仍有机会拦到。

### 2.3 证据

`test/v0239-publish-gate.test.ts` 里新增 5 条，整改前红：

```
not ok 7   test/ 下的真凭据形状必须阻断发布（整目录豁免已删除）
not ok 8   docs/ 下的真凭据形状同样阻断发布
not ok 9   例外只认「这个文件里的这一串假值」，同文件里换一把钥匙仍然失败
not ok 10  独立扫描器也不再对 test/ 整目录放行
not ok 11  例外表必须仍能对上真实文件
```

第 9 条是最关键的一条：先把真实仓库里登记过的文件原样复制进夹具（应当通过），再在**同一个
文件**末尾追加一把没有登记的 key（必须失败）。它同时证明「例外是逐字量」和「例外没有过期」。

`test/v0239-publish-gate.test.ts` 第 12 条在真实仓库上跑发布模式打包，结果是 834 个文件、
独立扫描器 0 发现 —— 证明收紧之后自家的包仍然打得出来。

## 三、`approved: false` 的写入语义

### 3.1 真实 diff

`git diff c372091..HEAD -- src/runtime.ts` 里所有涉及 `approved` 的行只有三行：

```diff
-          ...(reaimed ? entry.candidates.map((row) => ({ ...row, approved: false })) : entry.candidates),
+              ...(reaimed ? entry.candidates.map((row) => ({ ...row, approved: false })) : entry.candidates),
+            ? entry.candidates.map((row) => ({ ...row, approved: false }))
```

- 第一行是删除，第二行是同一表达式重新缩进（因为外层多了一个三元）；
- 第三行是新增的**撤销**分支：没有草稿且发生了重定向时，把旧候选全部置为未批准。

新候选的 `approved: false`（`src/runtime.ts:1742`，`candidateBase` 的字面量）与编辑路径的
撤销（`src/runtime.ts:2200`）都**不在 diff 里**，说明这两处没有变动。

### 3.2 静态不变量

`src/runtime.ts` 全文的 `approved` 写入只有 5 处：

| 位置 | 形态 | 语义 |
| --- | --- | --- |
| 1223 | `entry.candidates.map((row) => ({ ...row, approved: false }))` | 漂移时撤销 |
| 1742 | `approved: false,`（`candidateBase`） | 新候选初始化 |
| 1856 | `...(reaimed ? … approved: false …)` | 重定向且有新草稿时撤销 |
| 1860 | `? entry.candidates.map(… approved: false)` | 重定向且无新草稿时撤销 |
| 2200 | `approved: false,`（编辑路径） | 正文被改写后撤销 |

全文 **0 处** `approved: true`。授予批准只发生在 `src/index.ts`、`src/import/workflow.ts`、
`src/publisher.ts` 的显式操作里，不在生成链路。

`test/v0239-approval-invariants.test.ts` 把这两件事写成断言：不存在 `approved: true`；
每一处 `approved:` 必须是「新对象初始值」或「撤销映射」两种形态之一，出现第三种就失败。

### 3.3 行为证明

三条用例走真实 `runGeneration`：

1. 新生成的候选 `approved === false`。
2. 已批准一条候选，然后让模型返回 `needs_more_context`（不重定向）：候选数不变，
   **批准保留**。这一条防的是「顺手撤销」——那会让主人白批一次。
3. 已批准一条候选，重定向到另一个人并让模型拒绝：候选数不变，**旧批准被撤销**。
   这一条防的是「两句真话同时存在」：那段文字是写给上一个人的。

变异验证：把 `lib/runtime.js` 里的 `storeCandidate` 改成恒真（即恢复「无条件落候选」），
第 2、3 条立刻变红；恢复后转绿。说明这两条测的是行为，不是文本。

## 五、裸目录安装验证（执行时发现）

### 5.1 现象

`node scripts/verify-install.mjs` 从 v0.2.36 起退出码一直是 1：

```
✖ @deepseek-ai/dsh-llm 声明在 dependencies 里 —— 只声明在 peerDependencies 或完全没声明
✖ 本地可解析 @deepseek-ai/dsh-llm —— 开发依赖里没有，无法做安装自检
```

### 5.2 根因

`src/host-llm.ts` 里有一句注释，说明「故意不 import 那个类型」：

```ts
// 这里用结构化类型（HostLlmLike）而不是 import type { ... } from '@deepseek-ai/dsh-llm'
```

`verify-install.mjs` 的 `bareImportsIn` 对 `.js` 文本直接跑 `/from\s+'([^.'][^']*)'/g`，
把这句注释当成了依赖声明。发布物里从来没有这个运行时依赖，所以这是一个纯粹的误报。

误报的代价不是「多一条红」：这条脚本是「安装包能不能独立装上」的唯一自动化门禁，从 v0.2.36
到 v0.2.39 它一直红着，等于这条门禁不存在。

### 5.3 修法

新增 `scripts/lib/import-scan.mjs`：用一个小状态机区分「代码 / 字符串 / 注释」，字符串原样
保留、注释整段丢弃，再做导入匹配。正则做不到这件事 —— `//` 也出现在 URL 里，用正则剥注释
会吞掉 URL 后面的真导入。

`test/v0239-import-scan.test.ts` 5 条：注释里的 import 不算、块注释不算、字符串里的
`//` 不是注释起点、转义引号不提前结束字符串、目录扫描只收真依赖。

修复后 `node scripts/verify-install.mjs` 退出 0：解出 366 个文件、无自带 `node_modules`、
按声明装入 3 个包、从安装位置挂载 9 个工具与 43 个配置项。

## 七、边界与没有做的事

1. **例外表仍需要人判断「这条是不是假数据」。** 代码能保证「逐字、仍然存在、只在这个文件」，
   不能保证「人没有把真钥匙登记进来」。这是审查项（`source-zip.mjs` 属敏感路径），
   也是这次停在 PR 等维护者的原因。
2. **跨平台字节复现未验证。** 同平台同提交成立；Linux runner 与 Windows 的 zlib 差异没有对照。
3. **没有新增平台能力、没有重跑 Desktop。** 本轮只改打包器、扫描器、验证脚本、测试与文档，
   页面代码未动；Desktop 51/51 的证据仍是 v0.2.39 上一轮那次，不冒充本轮重跑。
4. **第 5 项（安装验证误报）是执行时发现的，不在任务书里。** 它影响的是「独立安装验证」
   这一条能不能算完成，所以一并修了；如果维护者认为它应当单独走一次审核，可以从 PR 里拆出。
