## 二、五项既有失败：逐条根因与修法

### 2.1 判定表

| 案例 | 旧行为 | 归类 | 根因 | 修法 | 现状 |
| --- | --- | --- | --- | --- | --- |
| `baseline/03` | 「该楼层里在主人发言之前没有其他参与者」，整条链路死掉 | **识别漏了** | `pickOpponent` 只看触发**之前**的发言；触发帖是这一层第 0 条时窗口为空 | 窗口里没有任何非主人发言时，回落到触发之后，并在 `notes` 里写明这是回落判断 | 通过 |
| `context/01` | 「依据我前面贴过了」被当成提问，论据丢失 | **识别漏了** | 关键词表把名词「依据」当疑问标记 | 名词性词（依据/证据/数据/理由）只在疑问框架里算问句 | 通过 |
| `refusal/04` | 对方只说「不同意」，零结构判红 | **案例本来没有证据** | 评分器把「漏读」和「本来没有」算成同一件事 | 案例声明 `evidenceState: 'insufficient'`；零结构成为正确结果，改判「替对方编立场」为红 | 通过 |
| `weibo/06` | 「涨了 44%」被判编造 | **算错了** | 评分器只做字面比对，把一次正确的除法当编造 | 数字追溯分 quoted / derived / unknown，只有 unknown 判红，算式写进依据 | 通过 |
| `quality/long-01` | 「忽略了迁移成本，这一块谁来付？」整句丢失 | **识别漏了** | 句子被判成提问就整句丢弃 | 先按分句切，陈述分句留、疑问分句丢 | 通过 |

### 2.2 确定性通道：五项归零

同一份 80 案例语料、同一个评分器：

| 指标 | v0.2.37 | v0.2.38 |
| --- | --- | --- |
| 确定性零分项（硬性失败） | **5** | **0** |
| target_accuracy | 0.969 | 0.969 |
| argument_recognition | 0.950 | 1.000 |
| stance_consistency | 1.000 | 1.000 |
| factual_credibility | 0.988 | 1.000 |
| non_repetition | 1.000 | 1.000 |
| uncertainty_handling | 1.000 | 1.000 |
| substantive_rebuttal（代理） | 0.115 | 0.117 |
| context_use（代理） | 0.148 | 0.151 |
| persona_style（代理） | 0.426 | 0.430 |
| naturalness（代理） | 0.972 | 0.972 |

**没有放宽任何断言。** 具体地：

- `argument_recognition` 从「只数三项（对方论据/未答问题/矛盾）」改成「八通道相加
  （含已答问题、质疑、跑题、第三方引用、谬误）」。这不是把标准调松 —— 一条什么都没
  找到的简报仍然是全零；改的是「测错了对象」，因为「有没有可用的结构」不等于
  「三个特定字段是不是非空」。
- `factual_credibility` 从「字面比对」改成「可追溯判定」，但**新增了产品侧的硬校验**
  （`fabricated_number`）：模型吐出的回复里，带百分号或带量词的数字必须能追回材料，
  否则整条候选被拒。也就是说，这一条从「只在评测里扣分」变成了「在产品里拦下」。
- `refusal/04` 的改判伴随着**新增一条检查** `asks_instead_of_inventing`：回复必须
  在追问、且没有替对方补立场。原来这个案例只要求「非空」。

### 2.3 回归测试

新增 `test/v0238-five-failures.test.ts`（9 条）：每条对应一项失败，注释写清
旧行为、根因、为什么那是错的；断言打在**导致失败的那个判断**上（问句识别、claim 抽取、
对手推断、数字追溯），而不是打在「分数是 1」上。

## 三、论证策略与人格解耦（§3）

### 3.1 结构

新模块 `src/strategy.ts`，8 种打法，每种带**证据门槛函数**（读的是已通过校验的简报）：

| 打法 | 门槛 |
| --- | --- |
| 指出已核实的前后矛盾 | `decisivePoints` 里 `quoted` + `high` 的矛盾 |
| 指出对方在重复已答的问题 | `answeredByOwner` 非空 |
| 提出有出处的反例 | `thirdPartyCitations` 非空 |
| 澄清双方定义 | 发现 `equivocation` 谬误 |
| 追问关键依据 | `missing_evidence` 类型的重点 |
| 解释争议前提 | 有分歧、但没有任何硬矛盾 |
| 直接回应核心论据 | 有可引用的对方论据 |
| 证据不足时提出澄清问题 | 兜底：恒可用 |

**顺序即优先级，依据是「证据有多具体」，不是「打法有多精彩」。**

开发过程中有一次自查：第一版把 `answer_core` 排在第三，结果 80 个案例里 70 个都选它
—— 因为几乎每层都有对方论据，这个门槛永远满足。那不是策略层，是一个恒真的分支。
把通用打法排到倒数第二之后，分布才有意义（见 §5）。

### 3.2 记录

每次选择都带三样东西并落库到候选的 `argumentStrategy`：

- 用了简报的哪个字段（`field`）；
- 哪几条 post（`postIds`）；
- 凭什么（`why`）、多可靠（`confidence`）、谁定的（`auto` / `manual`）。

与模型自报的 `strategy` 分两个字段：一个是自我描述，一个是系统决策记录。
合并就等于让模型的自我描述冒充决策记录。

### 3.3 手工指定

不满足门槛时**报错并说清缺什么**，不悄悄换成另一个 —— 否则主人会以为自己指定生效了。

### 3.4 正交性验证

新增 `test/v0238-strategy-persona-split.test.ts`（16 条）。其中三条钉正交：

1. 同一份简报，四种人格的提示词里出现**同一个**策略名（策略不随人格变）；
2. 同一个策略，四种人格的提示词里**打法段在前、人格段在后**，且打法段里不出现任何
   人格的名字（两段不互相渗透）；
3. 人格的 `approach` 不再包含「先……再……最后」这类打法叙述。

### 3.5 人格侧的收窄

`approach` 从「先钉住对方最虚的那一句，再要求把依据摆出来」改成「开口就直给，一句话
一个意思」。四种人格的 `approach` 仍然互不相同（测试钉住），但它们现在描述的是
**同一句话在不同人格下长什么样**，不是四种不同的打法。

## 四、长上下文与事实准确性（§4）

### 4.1 压缩记录

新模块 `src/compression-record.ts`。压缩前后逐项记录六项：

| 项 | 判据 | 依据等级 |
| --- | --- | --- |
| 目标评论 | 原文片段 + post id 都在材料里 | exact |
| 主人立场 | 简报 summary 的片段在材料里 | exact |
| 对手论据 | 第一条 claim 的片段在材料里 | exact |
| 来源 id | 立场与论据引用的 id 至少一个还在 | exact |
| 核心争议 | 分歧句的片段在材料里 | **proxy**（没有逐字原文） |
| 不确定信息 | 简报有没有报告缺口 | exact |

**判定范围包含简报**。第一版只量对话段，于是 `baseline/03` 被记成「对手论据丢失」——
而那条论据就在简报里，模型看得到。只量一段会得到与事实相反的记录，那种记录比没有更坏。

丢了东西才写进候选的 `notes`，并说明「回复在这一点上显得空，原因可能在这里」。

### 4.2 三条不变量（`test/v0238-long-context-retention.test.ts`，9 条）

1. **关键四项在三种预算下都不丢**（小/中/大）：目标评论、主人立场、对手论据、来源 id；
2. **压缩不补事实**：压缩后每一行对话都必须是某条原始发言的前缀（截断也算合规），
   数字只能是原文数字或帖子 id；
3. **代理判定必须标出来**：核心争议没有逐字原文，只能 `proxy`，不能冒充 `exact`。

### 4.3 事实准确性的产品侧收口

`src/number-trace.ts` + `validateDraft` 的 `fabricated_number`：

- 原文出现 → 允许；
- 由原文两个数算得出（差值 / 涨幅）→ 允许，算式写进依据；
- 追不回去 → **拦下整条候选**，并建议改成追问。

拦截面收窄到「带百分号或带量词」：编号（「第 3 节」）不是事实主张，一起拦会让正常
回复无谓被判红。收窄有代价（「三点五个亿」这种写法漏网），但宁可漏一种写法，也不要
误杀到主人关掉这条检查 —— 这一条写进代码注释，不是事后补充。

### 5.3 怎么读这张表（不许拔高）

**没有测出「新版更好」的证据。** 三件事必须说清：

1. **「命中具体要素」是四字片段的字符串匹配**。它奖励复述原文、惩罚改写。v0.2.38 的
   数字更低，一个可能的原因是策略层要求「只做一件事」，回复更集中、复述更少 ——
   但**这只是假设，没有被验证**。不能据此说新版更差，也不能说更接近论点。
2. **样本 20、单次采样，没有统计显著性**。两个版本各跑一次，连「稳定」都谈不上。
3. **§5 要求「盲评尽可能独立」**。这一轮满足了一半：判分器是代码、不认版本，
   但读回复的人（我）知道哪条是哪个版本 —— **不是盲评**。真正的盲评需要第三人。

### 5.4 真正测出来的差异：策略分布

v0.2.37 没有策略概念（`argumentStrategy` 字段不存在）。v0.2.38 的 19 条成功产出：

| 策略 | 条数 |
| --- | --- |
| 直接回应核心论据 | 14 |
| 追问关键依据 | 2 |
| 证据不足时提出澄清问题 | 2 |
| 解释争议前提 | 1 |

**这是这一版唯一一处有实证的改进**：同一个人格、同一批案例，系统不再只走一条路。
但它也只走到了「四种打法」——**没有达到「四种人格各走不同打法」**，而且那本来就不是
目标（§3 明确说不要强行让四种人格分别采用四种论证）。

### 5.5 一条真实的失败，以及它暴露的产品缺陷

`q06`（长楼层，最早那条质疑被 6 条刷屏埋住）**连续两轮都产出空正文**。

追查结果：模型按第 3 条铁律返回 `status: "needs_more_context"`，而离线链路只判断
「draft 存不存在」—— 存在就落库。于是：

1. 页面上出现一条可以点「复制」的空候选；
2. 采集器只能记下一条空正文，分不清「模型拒绝」与「链路坏了」；
3. 报告里的「20/20 成功」会是假的。

修法：`needsInput` 或正文为空时**不落候选**，把模型说的缺口带回给人。
新增 `test/v0238-empty-candidate.test.ts`（4 条）钉住。

**这一条是这一版最重要的产出之一**：它是真实模型跑出来的，不是设计时想到的。

## 六、真实 Desktop 验收（§9）

隔离 profile + 独立 store + 真实宿主模型，跑既有 51 阶段 GUI 链路：

```
结论：passed（失败 0，跳过 0，异常信号 0/0）
确认生效 — 按钮变为「已确认」
确认后复制可用 — 复制回复，disabled=false
复制有可读的反馈 — 已写入剪贴板并提示
四种人格都在结果里 — 4 个：贴吧老哥/小受/傲娇/高冷
打法下拉独立存在 — 9 个选项，自动项 有
```

**剪贴板是实际读回的**：用系统剪贴板读回 45 个字，与已批准候选逐字一致
（`说两边都有道理等于没站边。翻倍夸不夸张，那得看成本到底涨了多少，光说夸张解释不了任何东西。`）。

刷新后仍读得到这条会话，当前步骤「复制回复」；控制台异常 0 条。

### 6.1 这一轮抓到的两次「假红」

都记在这里，因为它们是**测试判据写错，不是产品错**：

1. **人格数成 12 个**：原来数页面上所有「名字 —— 说明」的选项。新增打法下拉用了同样
   的格式，于是 12 个并判红 —— 而人格依然正好四个。
2. **人格数成 0 个**：改成按 `option.value` 认下拉，结果是 0 —— 这个 React 版本里
   option 的 value 不按我们写的那样出现在 DOM 上。

最终判据改成**按可见文字找那个下拉**，并新增一条独立断言「打法下拉独立存在」（9 个
选项，含一个「自动」项）。两次红都不是产品问题，但它们各自暴露了一个判据错误 ——
如果当时为了变绿去改产品，就会做出两个不该做的改动。

### 6.2 一次真实的「编辑改错了框」

第一次桌面验收里「确认生效」失败。查下来：页面现在有三个 textarea，测试按「第二个
长度超过 20 的」取，取到了候选区之外的那一个。于是「编辑」改的是别人的框，候选正文
没变，确认自然对不上 —— 而报告读起来像确认功能坏了。

修法：按候选卡片里的「正文（可以直接改）」标签定位。

### 6.3 目标切换后旧候选失效

**本轮未单独验证。** 它由 v0.2.35 的输入指纹与批准绑定保证，且既有测试
（`v0235-generation-stale` 等）覆盖；但这一版没有再做一次真实的
「生成 → 改目标 → 看旧候选是否作废」的桌面步骤。**如实记为未测。**

## 七、源码包可复现性：根因（§7，v0.2.37 的遗留缺口）

### 7.1 事实链

| 观察 | 结果 |
| --- | --- |
| v0.2.37 本机重建 | 7815604 字节，SHA256 `49b7b1d7…` |
| GitHub 上的官方包 | 7813235 字节，SHA256 `3cd0bc11…` |
| 差多少 | 2369 字节 |
| 从**干净 LF 工作树**重建 | **7813235 字节，SHA256 `3cd0bc11…`** —— 与官方逐字节一致 |

### 7.2 原因

`.gitattributes` 要求 `eol=lf`，但**工作树里 20 个文本文件是 CRLF**（被工具以文本
模式重写过），而 `scripts/source-zip.mjs` 读的是工作树。

排除的其他可能：

| 怀疑 | 结论 |
| --- | --- |
| 文件内容不同 | 否。同一提交，内容一致，差异只在行尾 |
| 文件顺序不同 | 否。`git ls-files` 排序，两次一致 |
| 时间戳不同 | 否。ZIP 时间戳固定为 1980-01-01 |
| ZIP 元数据不同 | 否。OS 字段固定 255、权限固定 0644 |
| 构建工具或平台不同 | 否。同一台机器、同一个 Node |
| 未纳管产物 | 否。白名单 + `git ls-files` |

### 7.3 所以两句话都要改

- **「源码被篡改」是错的** —— 内容逐字节可复算，只是读错了基准。
- **「构建可完全复现」在当时也不成立** —— 可复现的前提是打包读的是提交内容，
  而不是作者硬盘上那一份。

### 7.4 这一版做了什么

1. `scripts/lib/archive-verify.mjs`：判定逻辑，四类分开（内容不同 / 只有行尾不同 /
   归档多出 / 归档缺失）；
2. `scripts/verify-source-archive.mjs`：独立核验工具，不 import 打包脚本的任何规则；
   `--drift` 在打包**之前**就能报出「工作树不是那个提交」，`--json` 输出逐文件清单；
3. `.gitattributes` 补 `* text eol=lf`，把**存储侧**也钉死，不再依赖 `core.autocrlf`；
4. 新增 `test/v0238-source-archive-integrity.test.ts`（11 条），其中一条在临时 Git
   仓库里把 LF 改成 CRLF，断言判据说的是「只有行尾不同」而不是「内容不同」。

### 7.5 仍然不能声称的

- **字节级跨平台复现**：依赖同一套 Node/zlib。构建环境（Node 版本、平台、命令）会记进
  清单文件，但「同一份源码在任何机器上产出同一串字节」这句话**没有验证过**。
- **`scripts/source-zip.mjs` 本身没有改**（它属于敏感路径，需要维护者授权）。
  因此「打包读工作树」这个根因**还在**，只是现在有工具能在打包前发现它。
  真正的修法是让它读 `git cat-file` 的内容 —— 那是一个 PR，不是顺手的一行。
