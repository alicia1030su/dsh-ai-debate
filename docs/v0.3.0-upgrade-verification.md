# v0.3.0 真实升级与批准边界验证

> 用**真实跑出来的 store**（不是手工构造的形状）验证升级：
> v0.2.39 的 30 条会话、v0.3.0 的一条已批准候选，分别用 v0.3.0 的 `lib/store.js` 读。
> 脚本在 `.ship/upgrade/`（gitignore），数据在 `tmp/quality/iso-9912`、`iso-9913`。

---

## 一、为什么用真实 store

单测 `test/v0300-upgrade.test.ts` 用的是手工构造的三份形状，能覆盖字段，但覆盖不了
「跑完之后磁盘上到底是什么」。这一轮的两个 store 是**产品自己写出来的**：

| store | 来源 | 内容 |
| --- | --- | --- |
| `iso-9912` | v0.2.39 安装包跑完 30 条固定案例后的落盘结果 | 30 个会话、26 个候选、`approvals: []` |
| `iso-9913` | v0.3.0 候选跑完 51 阶段 Desktop 验收后的落盘结果 | 1 个会话、5 个候选，其中 1 条 `approved: true` |

## 二、v0.2.39 → v0.3.0：30 条会话全部可读

```
旧 store 会话数: 30
v0.3.0 读出会话数: 30
每个 id 都能按原 id 读到: true
首会话标题一致: true | 成本上涨了，价格能不能跟着翻倍
首会话候选数: 1 （旧： 1 ）
首会话 state 一致: true
批准记录条数: 0 （旧： 0 ）
安全事件条数: 0 （旧： 0 ）
```

不是「条数相同」，是**每个 id 都按原 id 读得到**，且标题、状态、候选数与旧文件逐项相同。

## 三、旧批准不会变成新权限

v0.3.0 自己写出的 store 里有一条 `approved: true`（Desktop 验收时人工确认的那条）。
用 v0.3.0 的读取路径打开它：

```
读出的候选数: 5
读出 approved=true 的候选: 1 | replyId: m202611091511521z6k-c5
批准记录（ApprovalRecord）条数: 0
旧布尔值能否当授权: 否（没有批准记录，发表会被拒）
```

这条很关键：**布尔值读出来是 `true`，但它不构成任何发表授权。**

判据不是「读出什么」，而是「发表路径消费什么」：`src/publisher.ts` 要的是
`ApprovalRecord` —— 绑定正文哈希、目标快照、账号与时间，由 `createApproval` 在人工确认
那一刻生成。旧 store 里没有这种记录，`getApprovals()` 返回空，发表路径把「没有记录」
当作拒绝。

所以升级**不是**一次提权动作。v0.2.38 时代也验过同一件事（`v0239-upgrade-safety`），
这一轮用真实数据再验一遍，因为「旧批准的语义」是每次升级最容易被顺手放宽的地方。

## 四、回滚：v0.3.0 的 store 能被旧版本读吗

回滚的判据与升级相反——**旧代码不认识新字段时会不会崩**。既有测试
（`v0239-upgrade-safety.test.ts` 的「未知顶层键」一条）覆盖的是「多一个键不影响读取」，
v0.3.0 没有给 store 增加新的顶层键（`version` 仍是 `1`，字段集合与 v0.2.39 相同），
所以回滚的风险面没有扩大。

**这一条只做了结构比对，没有把 v0.2.39 的安装包真的装回去跑一遍。** 原因：v0.3.0 与
v0.2.39 的 store 字段集合逐键相同（`version/sessions/dedupe/usage/security/approvals/
verification`），差异只在候选的 `candidateVersion` 递增，而旧版本读候选时不校验该字段。
真要验证回滚，需要一次「装回 v0.2.39 → 打开同一 store → 读得出 30 条会话」的实跑，
**本轮没做，明确记为缺口**。

## 五、故障恢复：哪些做了、哪些没做

| 场景 | 状态 | 依据 |
| --- | --- | --- |
| store 损坏 | ✅ 有测试 | `v0239-upgrade-safety`：不静默覆盖，留 `*.corrupt-*` |
| 备份可恢复 | ✅ 有测试 | 同上：换回好文件后能正常读取 |
| 临时文件残留 | ✅ 有测试 | 同上：残留不影响启动 |
| 未知顶层键 | ✅ 有测试 | 前向兼容的底线 |
| 进程异常退出 | ⚠️ 未做 | 需要真的杀进程中途退出，本轮未执行 |
| 未完成的模型生成 | ⚠️ 未做 | 需要真实调用中途取消 |
| 配置写盘失败 | ⚠️ 未做 | 需要只读挂载或写满磁盘 |
| 会话文件部分损坏 | ⚠️ 未做 | 只验了整份 JSON 损坏 |

任务书 §7.2 要求的八项里，**四项有测试、四项未做**。不把「有测试」写成「八项全过」。
