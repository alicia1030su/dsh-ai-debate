## 一、微博 CLI 与 Provider 的断点（P0）

### 先证明再修

任务书要求先写能证伪的失败集成测试。`test/v0212-weibo-integration.test.ts` 在动代码前
跑出的结果：

```
✖ 断点：getThread 不得永远抛「未授权」——它必须先问 CLI 状态
   AssertionError: 不该笼统报「未授权」；实际 code=weibo_not_authorised
✖ 断点：适配器不得声明自己能读（能力必须来自 CLI 实测，不是常量）
   AssertionError: 能力缺失必须带可读原因，不能只是 false
```

两条红，证明断点真实存在：`provider.ts` 完全没有 import `cli.ts`，
`getCapabilities()` 是写死的字面量。

### 修复后

同一组测试全绿。真实链路现在是：

```
createAdapter()
  → resolveReadPlan()
       probeWeiboCli()            version + doctor
       listAvailableCommands()    commands list --available
       inspectCommand(候选)        commands show <name>  ← 校验必填参数
  → getThread()  → runReadCommand(cmd, [numericMid])   → projection.ts
  → getReplies() → runReadCommand(cmd, [mid, --page])  → projection.ts
```

### 不靠命令名猜权限（§一.3）

`classifyCommands` 只筛候选。真正的判定是 `inspectCommand`，它读该命令自己的参数表：

- 可填的参数只有两类：**帖子 id**（`id` / `idstr` / `mid` / `status_id` / `post_id`）
  与**分页**（`page` / `cursor` / `max_id` / `offset` / `count` / `limit`）；
- 其余必填参数（`uid`、日期范围、过滤器）→ 判为不可用，**并真的不调用**。

这里踩过一个坑：第一版把 `uid` 也归进「id 类」，理由是它确实是个 id。但 `uid` 是
**用户** id，不是要读的帖子 id——把它当可填，命令就会被以「只传了 mid」的方式调用，
真实 CLI 要么报错，要么读到别人默认的帖子。测试抓到了这一点。

有一条测试专门钉死这个行为：参数校验失败后，假 CLI 的调用日志里**不能出现**那条命令。

## 四、争论简报进入生成流程（P1）

### 缺陷

`brief.ts` 有类型、有校验器、有渲染器，**没有构建函数，没有调用点**。`validateBrief()`
只在测试里跑过。

### 现在的顺序

```
buildBrief(dispute, collected)      ← 新增 brief-builder.ts
  → validateBrief(brief, sources)
      ├─ 有问题 → 会话置 NEEDS_CONFIRMATION + 抛错，【不调用模型】
      └─ 无问题 → renderBrief → 注入 prompt「## 争论简报（已通过证据校验）」
```

**校验失败在调用模型之前**，有源码级测试钉住这个顺序（`buildAt < throwAt < llmAt`）。

### 路人不会被当成一方

`buildBrief` 用 `authorKey` 分侧；第三方被排除在两方立场之外，`bystanders` 单独输出，
**不推断站队**（从语气判断谁支持谁是猜测）。

## 五、微博诊断（§二）

本机真实输出：

```
[cli_missing]      weibo-cli 未安装：本机没有这个命令。
[not_implemented]  OAuth 登录：未知：CLI 未安装，这一项无法检查
[not_implemented]  开发者认证与服务：未知：CLI 未安装，这一项无法检查
[cli_missing]      正文读取命令：不可用
[cli_missing]      评论读取命令：不可用
[cli_missing]      没有安装 weibo-cli。这是最可能的原因：本机没有这个命令。
[not_implemented]  最近一次真实读取：本进程内还没有执行过（不代表失败，也不代表成功）
```

两条刻意的取舍：

1. **CLI 没装时，登录与服务是「未知」不是「未完成」** —— `doctor` 没跑过，我们没有
   证据。说「未完成」会让主人去找一个不存在的登录问题。
2. **额度报 `not_implemented`** —— 读余额要调官方账户/计费命令，属于账户管理，插件
   不代为执行。

七种状态都实现了区分：`not_implemented` / `cli_missing` / `not_authorised` /
`service_inactive` / `permission_insufficient` / `quota_exhausted` / `read_ok`。

## 六点五、独立审计发现并修掉的八个缺陷

微博接入代码交给了独立只读审计。审计报 4 个 P0、8 个 P1，我逐条在编译产物上实测复现——
**全部属实，全部是我这轮引入的真实缺陷**，均已修复并补了 11 项回归测试
（`test/v0212-audit-regressions.test.ts`）。

| # | 缺陷 | 实测复现输出 |
| --- | --- | --- |
| A1 | 未知分页状态被当成读完了 | 只有 comments 时 `hasMore === false`，采集器判定 `confirmed_end` |
| A2 | `data` 为数组时被读成零条 | 三条评论解析出 **0** 条，还误诊成「帖子被删」 |
| A3 | 只有 id 的空壳被当有效 | 投影出空正文 Thread，错误在分析阶段才暴露 |
| A4 | 平台返回的 id 可当命令行 flag | `idstr: '--output'` 被接受，argv 被搅乱 |
| A5 | schema 没解析出来 → 判为可用 | `usable: true, required: []` |
| A6 | JSON 解析错误未脱敏 | 错误消息带输入片段，会进日志与模型上下文 |
| A7 | openQuestions 方向渲染反 | 数据是「对方问、主人没答」，标题印「对方没有回答的问题」 |
| A8 | 回复关系解析后被丢弃 | `void repliedTo`，结构化信息白扔 |

另有两条同源 P0：`PAGE_LIKE` 无锚点匹配（`discount` 命中 `count`）且它判「可填」的参数
实际一个都不发；`--comment` 是凭空拼的 flag，目录里根本没有。填参策略已从正则改为显式
映射表 `FILLABLE_ARGUMENTS`（表里没列的参数一律不可填，且 argv 构造与适配器实际发送的
是同一份定义），父评论筛选参数改为从目录发现，目录没列就拒绝读取。

还有一条 P1：`incomplete` 被赋成 `hasMore`，导致**所有多页楼中楼永久假报「读不全」**。
