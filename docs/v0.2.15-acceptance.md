## 一、P0：源码 ZIP 泄漏（已修复）

### 缺陷

`scripts/source-zip.mjs` 遍历整个工作目录，只排除一份硬编码黑名单。`.env` 在任何一条规则里
都没出现，所以它带着完整内容进了**公开**源码包。

### 复现（修复前，真实执行）

在项目根创建 `.env`、`.env.local`、`.credentials.json`，执行 `node scripts/source-zip.mjs`：

```
文件数：471
.credentials.json
.env            ← 泄漏
.env.local      ← 泄漏
```

### 根因

**极性反了**。黑名单永远不完整：开发者本地可能创建什么文件是无限的，而每一次遗漏都是一次
公开泄漏。任务书要求「无法确认是否适合公开时默认不包含」——那只能是白名单。

### 修法

`scripts/source-zip.mjs` 重写：

| 要求 | 实现 |
| --- | --- |
| 不允许遍历全目录直接打包 | 白名单：只发 `src/`、`test/`、`scripts/`、`docs/`、`client/`、`templates/`、`.github/` 与指定顶层文件 |
| 优先用 Git 已跟踪清单 | 若是 Git 仓库，`git ls-files --cached -z` 为权威来源 |
| 无 Git 时安全回退 | 同一套白名单规则作用于目录遍历（本机即此路径） |
| 无法确认就不包含 | `isPublishable()` 对未知路径返回 `false` |
| 排除点文件/私钥/令牌/日志/备份 | `FORBIDDEN_NAMES` + `FORBIDDEN_DIRS`，在**白名单之后**再过一遍 |
| 保留 README/LICENSE/源码/测试/CI/脚本 | `ALLOWED_FILES` + `ALLOWED_DIRS` 显式列出 |
| 防符号链接逃逸 | `entry.isSymbolicLink()` 先于一切判断；`lstat` 对 Git 路径二次确认 |
| 公开前检查实际文件列表与内容 | 每个候选文件字节级扫描 `SECRET_PATTERNS` |
| 不得只靠正则 | 白名单是主控制，正则只是第二道 |
| 发现敏感内容构建失败 | `throw`，不是 `console.warn` |

另外加了两道闸：

- **最终清单复核**：`files` 组装完再按禁止规则过一遍。`isPublishable` 与它若不一致，
  说明有代码绕过了检查——这类回归值得直接失败。
- **独立扫描器** `scripts/scan-archive.mjs`：不导入打包脚本的任何规则，用自己的名单与正则
  检查**成品压缩包**。自证是不够的，因为「白名单写错」和「自检也写错」是同一个 bug。

### 验证（修复后）

```
文件数：471 → 239
.env 存在: false
.credentials.json 存在: false
.env.example 存在: true
导出的 LICENSE / package.json / .github/ 均在
```

`scan-archive.mjs` 对 tgz（247 条目）与源码 ZIP（239 条目）均返回「未发现敏感文件或凭据」。

### 新增测试

`test/v0215-source-zip-security.test.ts`（8 项）：

1. `.env` 不会进源码包
2. 私钥 / SSH / `.dsh` / 日志 / 备份 / `.npmrc` / `.netrc` 全部排除
3. 该保留的仍在（防「空包也算安全」）
4. ZIP 字节里不含假凭据内容（不只比文件名）
5. 符号链接不被跟随

## 二、P1：微博身份字段语义（已修复）

### 缺陷

`idsOf()` 把 `id`、`idstr`、`mid` 平铺进一个数组，**任一命中即放行**。审计复现：

```json
{ "idstr": "4331051486294436", "id": "9999999999999999", "text": "测试正文" }
```

v0.2.14 返回 `ok: true`。这个对象自己说自己是两条不同的微博。

### 字段语义的依据

微博开放平台 CLI 手册（https://open.weibo.com/cli/manual ）明确要求「发布后请保存 id/idstr」，
把两者并列为**同一个标识的两种形式**；而 `mid` 出现在 `weibo.com/<uid>/<mid>` 形式的 URL 里，
属于**另一套编号**（mid → id 需要换算）。

| 字段 | 语义 | 同空间于 |
| --- | --- | --- |
| `id` | 微博状态 ID | `idstr` |
| `idstr` | 同一 ID 的字符串形式 | `id` |
| `mid` | URL 中的 mid | 仅 `mid` |

### 修法

- **同语义组内冲突必须拒绝**：`id` 与 `idstr` 同时出现却不同 → `identity_conflict`。
- **跨语义组不强制比较**：`mid` 与 `id` 取值不同是正常的，不得因此拒绝（这是过度校验）。
- **矛盾检查先于匹配**：审计 payload 的 `idstr` 等于请求值，若先判「有没有字段命中」，
  命中字段会盖住矛盾。先问「这个对象自洽吗」。
- **重复对象作者也纳入比较**：v0.2.14 只比正文，同 id 挂两个作者时通过——那正是「谁是对手」
  会被判错的情形。
- **嵌套信封**：`{ data: { status } }` / `{ result: { statuses } }` 现在能穿透，最多 4 层。

### 新增测试

`test/v0215-weibo-identity.test.ts`（19 项），覆盖：

- 审计原始 payload → 拒绝，`code: identity_conflict`
- 三种正常形状（只有 id / 只有 idstr / 两者一致）全部接受
- 批量里一条矛盾、一条正常 → 正常的仍可用
- `mid` 与 `id` 不同 → 接受（不过度校验）
- 按 `mid` 命中时报告 `matchedOn: 'mid'`
- `mid` 命中但 id 组矛盾 → 仍以矛盾为准拒绝
- 重复对象：正文一致接受 / 正文矛盾拒绝 / 正文同作者不同拒绝
- 嵌套结构：单层、列表、嵌套里的冲突、无微博对象
- 集成：冲突时 `getThread` 抛 `target_mismatch`，不产出可分析 thread

原有 16 项身份测试全部保留并通过。

## 三、P1：CLI 参数形状 ≠ 真实平台验证（已修复）

### 缺陷

`nestedClaimOf()` 只要命令同时声明 `cid` 和 `count` 就返回 `state: 'verified'`、
`available: true`；而 `provider.ts` 用的是 `nestedClaim.available === true`。于是**页面宣称
「子评论可读」，而那次读取从未执行过**。

### 六层证据

任务书要求的六个层次，前两层静态、后四层必须来自真实调用：

| 层次 | 性质 | 本轮状态 |
| --- | --- | --- |
| 1. 命令存在 | 静态（`commands list`） | 可判定 |
| 2. 参数 Schema 兼容 | 静态（`commands show`） | 可判定 |
| 3. 已取得账号权限 | 账号态 | `unknown`（catalogue 未说明） |
| 4. 真实调用成功 | 网络 | 未发生 |
| 5. 父子关系正确 | 网络 | 未发生 |
| 6. 真实平台验证完成 | 人工确认 | 未达成 |

### 修法

`CapabilityClaim` 增加 `evidence`：

```
evidence: {
  commandExists, schemaCompatible, accountPermitted: boolean | 'unknown',
  liveCallSucceeded, parentChildConfirmed,
  level: 'schema_only' | 'live_call' | 'fully_verified' | 'unavailable'
}
```

- 所有静态构造点一律 `schema_only`（`liveCallSucceeded: false`）。
- `provider.ts` 的 `nestedReplies` 改为只认 `evidence.level === 'fully_verified'`。
- **一次成功的调用也还不够**：`live_call` 只证明命令能跑，不证明返回的回复真的挂在那条评论下。
- 新增 `describeEvidenceLevel()`，让 `schema_only` 的措辞明确写着「尚未在真实平台调用」。

### 新增测试

`test/v0215-capability-evidence.test.ts`（13 项）：

- `cid` + `count` 齐备时 `available` 仍为 true **但** `level` 必须是 `schema_only`
- 无父参数 → `unavailable`；有父参数无配套 → `unverified`
- 账号权限默认 `unknown`（缺标记不等于有权限）
- `capabilityEvidence()` 四种层次的计算
- 矛盾组合（调用过但 schema 说不支持）取**最弱**答案
- 省略参数时全部取最弱值
- `schema_only` 的措辞不得出现「已验证可用」

1. 安装 Git for Windows（含 `git`）与 GitHub CLI（含 `gh`）。
2. `git init && git add -A && git commit -m "v0.2.15"`。
3. `gh auth login` —— 选 `GitHub.com` → `HTTPS` → `Login with a web browser`，在浏览器里粘贴一次性代码。
4. `gh repo create dsh-ai-debate --private --source . --push`。
5. `gh run list --workflow CI` 查看运行结果。

推送与发布**需要用户自己做**：任务书要求这类操作事先取得批准，而本环境无法取得。

## 五、CI 真实性加固

`scripts/ci-guard.mjs` 把六类「绿色但什么都没验证」变成可断言的仓库属性：

| 空检查 | 检查方式 | 本轮发现 |
| --- | --- | --- |
| 测试文件遗漏 | 磁盘 `*.test.ts` 与 runner 实际执行数比对 | 无遗漏（85 个） |
| 进程崩溃仍报成功 | 禁止 `\|\| true` / `continue-on-error: true`；多行步骤必须 `set -e` | **3 处缺 `set -e`** |
| 构建与源码不一致 | `.gitignore` 不得排除 `lib/`；工作流必须有 `git diff --exit-code lib/` | 通过 |
| 锁文件不完整 | 每个依赖都在 `pnpm-lock.yaml`；安装用 `--frozen-lockfile` | 通过（8 个依赖） |
| 发行包含无关文件 | release 校验必需文件并拒绝 `src|test|scripts|node_modules` | 通过 |
| 安全扫描未覆盖源码 ZIP | 两个工作流都必须调用 `scan-archive.mjs` | **两个都没调用** |
| Release 在 CI 失败时仍可发布 | 创建 Release 必须限定 `refs/tags/` | 通过 |
| 手动触发默认非 dry_run | `workflow_params.dry_run.default: true` | 通过 |

### 修掉的三个真实缺口

1. `ci.yml` 的「自动化测试」步骤是多行（注释 + 命令）但没有 `set -e`。
2. `release.yml` 的「自动化测试」同样缺 `set -e`。
3. `release.yml` 的「确认 lib/ 与源码一致」缺 `set -e`——这一步失败后若无 `set -e`，
   后续成功命令会让整步变绿，正是「lib 陈旧却报告通过」。

### 两处工作流强化

- `ci.yml` 现在**每次推送**都构建并独立扫描源码 ZIP 与 tgz。此前只有 release 才生成源码包，
  打包器坏了要等发版才发现。
- `release.yml` 在创建 Release **之前**插入独立扫描与守卫检查。发布路径多一道闸。

`test/v0215-ci-integrity.test.ts`（15 项）把这些断言固定下来。
