# v0.2.17 验收报告：把交付流程本身做成可执行的脚本

> 本文件只写「为什么这样做」和「哪些事被真的验证过」。
> **会变的数字（提交 SHA、PR 编号、Run ID、附件哈希）不写在这里** —— 报告写在提交里，
> 无法写下自己所在提交的 SHA，这类数字注定对不上（v0.2.16 的「发布提交 `f1c111c`」就是这么错的）。
> 那些数字在发布当时由工作流生成，见 Release 附件的 `delivery-status-0.2.17.json`。

---

## 一、这一版要解决什么

v0.2.16 之前，每次交付都靠对话里逐条下令：建分支、跑检查、提交、推送、开 PR、等 CI、
合并、打标签、看 Release。这套流程能走通，但它依赖「某个人此刻记得该做什么」，
并且**只在打标签的那一刻才第一次执行**的部分最容易出错 —— v0.2.16 的两个真实缺陷
（`upload-artifact` 拒绝 `..` 路径、gzip 头 OS 字节导致产物不确定）都是这样漏出去的：
CI 一直是绿的，因为它们根本不在 CI 里跑。

v0.2.17 把它做成 `scripts/ship.mjs`：一条命令走完十二个阶段，
每个阶段失败都留下状态与恢复建议，并且**该停下的地方一定会停**。

## 二、能自动化的与不能自动化的

自动化的：分支、构建、类型检查、全部测试、凭据扫描、双包构建与独立扫描、
提交、推送、开 PR、启用 GitHub 原生 auto-merge（squash）、等必需检查、合并、
打标签、发 Release、核验附件。

**不自动化的（这是设计，不是遗漏）**：命中敏感路径的改动会停在 PR 等维护者点头。
`scripts/lib/ship-core.mjs` 的 `SENSITIVE_RULES` 覆盖工作流文件、Actions 配置、
扫描器与打包器、交付流水线自身、`src/security/**`、真实平台的发表代码、`cordis.patch.yml`。
理由写在 CHANGELOG 第三节：**让改门禁的提交绕过门禁合进去，比任何一次失败的自动化都危险。**

v0.2.17 自己的改动全部命中敏感规则，所以它本身也会停在 PR —— 这一版就是这条规则的一次实测。

## 三、真被验证过的事

### 3.1 本地质量门禁

| 检查 | 结果 |
| --- | --- |
| `tsc -p tsconfig.json` | 通过 |
| `node scripts/test-typecheck.mjs`（测试类型检查，棘轮） | 316 条，等于基线，通过 |
| 全部自动化测试 | 1225 项，0 失败，0 跳过 |
| `scan-archive.mjs` ×2（独立规则，不 import 打包器） | 两个包均未发现敏感文件或凭据 |
| `ci-guard.mjs --require-archive` | 通过（94 个测试文件、锁文件覆盖 8 个依赖、源码包含锁文件与 232 个编译产物） |
| `audit-leaks.mjs` | 无凭据材料 |
| `version.mjs check` | package.json / CHANGELOG / README 三处一致 |
| `release-dry-run.mjs` | 通过，未创建 Release、未访问网络 |

测试总数从 v0.2.16 的 1067 涨到 1225，新增的 158 项全部针对本版新增的交付逻辑与门禁本身。

### 3.2 五类异常路径（`test/v0217-exception-paths.test.ts`）

每一类都真有代码在执行，不是「assert 一个常量等于它自己」：

1. **故意失败的测试** —— 真跑一个必失败用例，确认退出码非 0，且交付状态报告会拒绝把
   「失败数为 1」写成 `success`。
2. **凭据扫描失败** —— 造一个含 `package/.env` 的 TGZ，确认独立扫描器非 0；再造一个干净 TGZ，
   确认它**仍然放行**（否则等于奖励一个永远失败的扫描器）。再往白名单目录里写一段
   AWS 访问密钥形状的内容，确认源码打包直接失败。
3. **网络中断 / 进程被杀** —— 状态机可从 `.ship/state.json` 恢复，版本不符时
   `restoreState` 返回 `null` 而不是假装续跑。
4. **重复发布** —— 标签已指向别处时 `decideTag` 返回 `refuse`（**不移动标签**）；
   Release 附件字节数与本机不一致时 `decideRelease` 返回 `refuse`（**不覆盖已有发布**）。
5. **缺少授权** —— 命中敏感规则时 `nextStep` 返回 `blocked: true` 且理由里写明需要授权；
   不敏感时 `blocked: false`；每个阶段的 `blocked` 都是显式布尔值。

这三条测试里有两条第一次跑是红的，都是真发现：
子进程继承 `NODE_TEST_CONTEXT` 会让「故意失败」以退出码 0 结束；
`AKIAIOSFODNN7EXAMPLE` 会被 `FIXTURE_MARKER`（含 `example`）放行。

### 3.3 发布说明生成的忠实度

把 `release.yml` 里内联的 `awk` + `echo` 换成了 `scripts/lib/release-notes.mjs`，
由 `scripts/release-dry-run.mjs` 驱动，CI 每次推送都跑。

忠实度用已发布的 v0.2.16 反向验证：用同样的 CHANGELOG 与两个现成产物跑一遍，
产出的两个哈希与 v0.2.16 Release 页面上的附件**完全一致**（4185 字符 / 132 行）。
这说明重构没有改变输出，只是把「只在打标签时才执行」变成「每次推送都执行」。

### 3.4 交付状态报告

`scripts/delivery-status-report.mjs` 生成机器可读 JSON，未知一律写 `null`（不写占位字符串，
`0` 也不算 —— 那会被当成「测过了，零失败」）。

它有一条自我约束：声称 `success` 却不自洽（没有提交、没有标签、附件为空、测试数为 0、
有失败数）时，**把自己的状态改成 `failed` 并以退出码 1 结束**。宁可变红，也不发出可疑证据。

本机第一次跑就被这条约束拦住了两次，两次都是真问题：
① 本机 `node --test > log.txt` 在 PowerShell 下写出的是 UTF-16LE，按 UTF-8 读会把
「1225 项全过」读成「测试数为 0」；② 没有标签引用时它拒绝报 `success` —— 这个降级是对的，
没在版本标签上跑，就没有「发布成功」这回事。

## 四、被测出并修掉的真实缺陷

| 缺陷 | 怎么发现的 | 后果（若未修） |
| --- | --- | --- |
| `advanceState` 只返回新对象，调用方忽略返回值 | 写单元测试时 | 每次阶段推进都被丢掉，`--resume` 永远从 preflight 重来 |
| `collectChanges` 用 `git diff` 看不到未跟踪文件 | 自查 | **新建** `.github/workflows/*.yml` 被判成不敏感，自动合并直接绕过授权 |
| `waitForMerge` 不检查仓库是否配了必需检查 | 真实 `gh api` 查询 | 没有必需检查时 `gh pr merge --auto` 立刻合并，「等 CI 绿」在配置层面不成立 |
| `tsconfig.test.json` 继承了基配置的 `exclude` | 子智能体审计 | 测试类型检查这道闸门跑了很久，一个测试文件都没检查 |
| `gh` 输出是 UTF-16LE | 实测 | 所有 `JSON.parse(gh 输出)` 静默得到空对象，检查表永远是空的 |
| 发布说明只在打标签时执行 | v0.2.16 的失败发版 | 写错了要等一次公开的失败才知道 |

## 五、仓库侧的策略变更（需要维护者知情）

为了让 auto-merge 真的等于「等必需检查通过再合并」，仓库做了两处设置：

1. **打开 `allow_auto_merge`**（原来关闭，关闭时 `gh pr merge --auto` 不可用）。
2. **新建 ruleset「main 保护：必需检查 + 禁止删除 + 禁止强推」**：
   必需检查是 `编译与测试（Node 22.18）` 与 `编译与测试（Node 24）`，
   禁止删除分支、禁止强推，`bypass_actors` 为空（任何人都不能绕过）。

**刻意没有勾 Require approvals**：本仓库只有一个维护者，勾了之后 auto-merge 永远等不到人，
自动化就变成「必然卡住」。这不是放宽门禁 —— 门禁是必需检查，而 approvals 在这里会自我阻塞。

`ship.mjs` 在合并前会真的去读 ruleset，**找不到必需检查就直接失败**并给出配置链接，
而不会退化成「反正 CI 绿了就直接合」。这一点写在 CHANGELOG 第二节。

## 七、这一版怎么发布

v0.2.17 的改动全部命中敏感规则，因此 `ship.mjs` 会在 PR 阶段停下（不启用 auto-merge），
等维护者看过 PR、看过 CI 的两个 Node 结果之后再合并。合并后由 `ship.mjs --resume`
继续打标签、发 Release、核验附件。

`--resume` 会从 `.ship/state.json` 记下的阶段继续，并且在继续之前重新算一次两个产物的哈希 ——
`verify` 阶段被跳过时附件列表会是空的，而空列表永远满足「每个附件都对得上」，
那会让附件核验静默通过。
