# 工作台标准操作接口（v0.2.22 前置）

> 这份文档是给下一个版本用的**接口约定**，不是现状说明。写它的原因是：v0.2.21 之后，
> 「发表」「验收」「批准」这三件事各自有了独立的入口和独立的证据来源，如果 v0.2.22 的
> 工作台再各写一套，就会出现第三份真相。
>
> 约束：本文只描述**已经存在并已有测试**的接口，未实现的会明确写「未实现」。把设想写成
> 现状是这类文档最容易犯的错。

## 一、三条读接口

| 接口 | 方法 | 权限 | 返回什么 |
|---|---|---|---|
| `/api/dsh-ai-debate/settings` | GET | 主人会话 | 配置视图（凭据只出掩码） |
| `/api/dsh-ai-debate/status` | GET | 主人会话 | 诊断块，含 `platforms[]` |
| `/api/dsh-ai-debate/verification?platform=<id>` | GET | 主人会话 | 验收视图 + 机器可读 `report` |

三条都走同一个 `guard`：回环地址、同源 Host/Origin、已验证的 DSH 浏览器会话。
**没有一条能由 agent 调用**——工具层不暴露它们，也没有客户端指向它们。

### `/verification` 返回结构

```jsonc
{
  "ok": true,                     // 只表示「没有阻断项」，不表示「已验证」
  "liveAccountId": "…",           // 当前会话真实登录的账号；读不到就没有这个字段
  "configuredAccountId": "…",     // 配置里要用的发帖账号 —— 与上面是两个不同的事实
  "adapterVersion": "1a2b3c4d",   // publishReply + getReplyContext 的源码指纹
  "capabilities": [
    { "capability": "comment.publish", "declared": "unverified", "effective": "unverified", "reason": "…" }
  ],
  "records": [ /* 每一次验收尝试，含 pending / succeeded / failed / uncertain */ ],
  "blockers": ["还没有配置 … 的发帖账号 id …"],
  "report": {
    "platform": "tieba",
    "generatedAt": "2026-10-31T12:00:00.000Z",
    "capabilities": [
      { "name": "comment.publish", "declared": "unverified", "effective": "unverified",
        "evidence": [ { "at": "…", "accountId": "…", "adapterVersion": "…" } ] }
    ]
  }
}
```

两条规矩，工作台必须遵守：

1. **`declared` 是天花板，`effective` 是这次能不能过。** 工作台只能展示 `effective`，
   绝不允许写回 `declared`——静态声明在运行时不改写，这是 §三.10。
2. **未知一律 `unverified`，不用 `null`。** 一个把未知渲染成绿勾的界面，比不渲染更糟。

## 二、两条写接口

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/dsh-ai-debate/approve` | POST | 为一条候选建立人工批准记录 |
| `/api/dsh-ai-debate/action` | POST | `test-llm` / `check-login` / `refresh-platforms` / `preview-personas` / `pause-now` / **`verify-publish`** |

### `verify-publish` 的请求体

```jsonc
{
  "action": "verify-publish",
  "platform": "tieba",
  "capability": "comment.publish",        // 或 comment.reply
  "authorizedAccountId": "…",             // 必填，主人提供
  "authorizedThreadId": "…",              // 必填，主人提供
  "authorizedFloorId": "…",               // 仅 comment.reply 必填
  "replyToPostId": "…",                   // 仅 comment.reply 必填
  "authorizedBy": "…",                    // 授权人，必填
  "approvedText": "…"                     // 逐字批准的正文，必填
}
```

**工作台不得为任何一项填默认值。** 账号、帖子、楼层、目标、正文五项都是主人手填——
填一个默认值就等于让代码替主人决定发到哪、发什么。缺项由服务端拒绝并回一句人话。

返回：

```jsonc
{ "ok": true, "upgraded": false, "message": "已发表，但回读证据不完整：…",
  "publishedPostId": "…", "readBack": { "postFound": true, "authorMatched": true,
  "textMatched": false, "parentMatched": true, "notes": ["正文不符"] } }
```

`ok: true` 只表示「发表请求确实出去了」。是不是验证通过，只看 `upgraded`：
它要求回读四要素全部成立。工作台必须把这两个字段分开渲染，否则「发出去了」会被读成
「验证通过了」。

## 三、失败与不可重试

| 情形 | 记录 | 工作台应显示 |
|---|---|---|
| 拒绝（授权缺项 / 账号不符 / 已用过 / 状态不对） | 不写记录 | 拒绝原因原文 + 该补哪一项 |
| 发表抛错（超时、403、验证码） | `uncertain` | 「可能已经发出去了，不会重试」 |
| 平台返回失败 | `failed` | 平台给的原因 |
| 没有 post id | `uncertain` | 同超时 |
| 发表成功、回读不全 | `succeeded` + `readBack` 有 false | 逐项列出哪一项没确认 |

**工作台不得提供「重试」按钮。** 一次授权只能发一次；要再验，必须由主人重新指定授权，
这是这一版专门做的防护，界面上不能留一条绕过去的路。

## 四、批准与模式

v0.2.21 起，`single_shot` 与 `limited_auto` 都**必须**逐条人工批准：

| 候选判定 | `manual` | `single_shot` | `limited_auto` |
|---|---|---|---|
| `block` | 拒绝 | 拒绝 | 拒绝 |
| `review` | 需要批准 | 需要批准 | 需要批准 |
| `allow` | 需要批准 | 需要批准 | **需要批准** + 本会话条数上限 + 冷却 |

`limited_auto` 因此只剩下「更严格」的含义，不再有「绕过」的含义，并被标为实验能力。
工作台不要把 `limited_auto` 渲染成「不打扰你」，那是 v0.2.20 及以前的说法。

## 五、v0.2.22 工作台应当遵守的六条

1. 读三条接口都要处理「读失败」：空数组和读失败必须长得不一样。
2. 验收区必须显示 `adapterVersion`：同一个账号换了实现，旧证据就失效了，藏起来等于骗人。
3. 验收表单的五个字段全部手填，不做记忆、不做预填、不做「上次用的」。
4. 一次验收一次提交，提交后按钮置灰直到有结果；不提供并发提交。
5. 「发出去了」与「验证通过」分成两个视觉层级，`upgraded` 才是绿的。
6. 任何把 `unverified` 渲染成通过、把 `null` 渲染成没问题、把 `limited_auto` 渲染成免批准
   的做法，都属于本文件的禁止项。

## 六、当前未实现

- **贴吧真实发表。** 本机出口访问 `tieba.baidu.com` 全部 403，验收的语义正确性由假适配器
  驱动的测试保证，真机证据仍是空的。这一条不能用模拟结果替代，验收报告里也把它单列为
  「受阻」而不是「通过」。
- **微博的 `comment.publish` 验收。** 微博适配器目前不声明这个能力，验收流程对它返回
  「不是 unverified，这次验收证明不了任何东西」。
- **发表工作台本身。** 本文描述的是接口，不是界面。v0.2.22 要做的是把它们组装成一条
  可操作的路径（候选预览/编辑 → 重新批准 → 发表一次 → 回读 → 结果），现在只有分立的
  页面区块与路由。

## 七、v0.2.21 补齐的三条安全性质（实现说明，供 v0.2.22 依赖）

v0.2.21 之后，下面三条已经由代码与测试保证，v0.2.22 的工作台可以直接依赖：

1. **授权抢占是原子的。** `DebateStore.claimVerificationRecord()` 在一个锁持有期内完成
   「查重 + 写入 pending」。同一份授权并发提交时只有一个能进入 `publishReply`；100 次并发
   的测试断言发表次数严格等于 1。工作台因此可以放心地允许用户点按钮，而不必自己做去重。
2. **登录账号未知即拒绝。** 读不到真实登录账号时返回 `account_unknown`，不写 pending、
   不调发表接口。配置账号与实际登录账号是**两个不同的事实**，视图里分别叫
   `configuredAccountId` 与 `liveAccountId`，不再互相顶替。
3. **验收证据接进了正常发表闸门。** `assertCapability()` 在声明为 `unverified` 时，会用
   「实时账号 + 能力名 + 适配器版本 + 持久化记录」计算有效能力；证据只能满足声明，不能
   改写它，也提升不了 `unavailable` 与 `permission_required`。换账号或换实现，旧证据立即
   失效。每一笔真实发表仍然需要人工批准 —— 能力提升不绕过批准。

工作台在展示时应当把 `declared` 与 `effective` 分开渲染，并把「为什么这次能过」的
`reason` 原文显示出来（它由 `capability-evidence.ts` 生成，和设置页、诊断报告同源）。
