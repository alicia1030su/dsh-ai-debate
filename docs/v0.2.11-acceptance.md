## 一、微博 ID 分段算法（P0）

### 复现（先失败）

用 v0.2.10 的编译产物跑审计给的样例：

```
Hd1N2qpta   expect 4331051486294436  got 9434507256622692  WRONG
I1IGF4Ud1   expect 4404101091169383  got 9613024555285431  WRONG
```

### 根因

「整体 base62 整数」与「分段 base62」是两个不同的函数。旧实现把整个 id 当一个 62 进制
数，而微博的规则是：数字 mid 从右每 7 位一组、每组转 base62、非最左组补 4 字符。

这个错法**自洽**——编码器和解码器互为逆运算，所以往返测试全部通过，只有拿外部算出来的
数字比才会暴露。

### 修复后

| base62 | numeric mid | 解码 | 编码 |
| --- | --- | --- | --- |
| `Hd1N2qpta` | `4331051486294436` | ✅ | ✅ |
| `I1IGF4Ud1` | `4404101091169383` | ✅ | ✅ |

手算复核（第二组证明了补位规则真的生效）：

```
I1IGF4Ud1 分组 ["I","1IGF","4Ud1"]
  I    = 44
  1IGF = 410109 → 补 7 位 → 0410109
  4Ud1 = 1169383
  拼接 = 44 0410109 1169383 = 4404101091169383
```

`410109` 只有六位。补位规则若不存在，这组必然失败——这条细节是分组算法不可省略的证据。

### ⚠️ 任务书第三组样例与算法不自洽

`Is0XboARR ↔ 4467107636950632` 两个方向互相得不到对方：

```
解码 Is0XboARR = 44 | 6676853 | 5861595 = 4466768535861595
编码 4467107636950632 = "I" | "s9M7" | "taaY" = "Is9M7taaY"
```

这是可以手算复核的。前两组已经足够确定算法（且第二组锁住了补位细节），所以我按前两组
实现，**第三组没有写成断言**——把错的期望写进测试等于把 bug 固化。如果第三组才是对的，
那我需要新的样例来说明规则不同在哪里。

### 反向验证

把算法退回 v0.2.10 的整体 base62 后，`v0211-weibo-mid.test.ts` 有 **8 项变红**
（解码方向、补位、精度、规范链接若干项）。这证明测试确实抓得住那个缺陷。

## 二、规范链接自相矛盾

**缺陷**：`parseWeiboUrl` 总是产出 `weibo.com/<numeric mid>`，而它自己的解析器拒绝纯
数字单段（那也可能是用户主页）。`parseWeiboUrl(parseWeiboUrl(x).url)` 对每个移动端链接
都失败。

**修复后实测**：

| 输入 | 规范链接 | 再解析 |
| --- | --- | --- |
| `https://m.weibo.cn/detail/4331051486294436` | 同左（无 uid，用详情路径） | 同一 threadId ✅ |
| `https://weibo.com/1234567890/Hd1N2qpta` | 同左（有 uid，base62） | 同一 threadId ✅ |
| `https://weibo.com/Hd1N2qpta` | `m.weibo.cn/detail/...` | 同一 threadId ✅ |
| `https://m.weibo.cn/status/4331051486294436` | `m.weibo.cn/detail/...` | 同一 threadId ✅ |

不编造 uid，纯数字单段的歧义拒绝保持不变。

## 四、微博官方 CLI 只读接入

### 本机真实状态

| 探测项 | 结果 |
| --- | --- |
| `weibo-cli` 是否存在 | **不存在**（`weibo-cli`、`weibo`、`weibocli`、`wb-cli` 全部 not found） |
| npm | **不可用**（因此也无法安装） |
| 开发者认证 | 无 |
| OAuth 登录 | 无 |
| 真实读取 | **一次都没有执行** |

`probeWeiboCli()` 在本机的实测输出：

```json
{
  "status": "cli_missing",
  "message": "没有安装 weibo-cli。这是最可能的原因：本机没有这个命令。",
  "canRead": false,
  "steps": 5
}
```

### 已实现的能力（代码层）

- CLI 检测（区分 `cli_missing` / `not_authenticated` / `service_inactive` /
  `quota_exhausted` / `command_unavailable` / `failed`）
- 命令发现（`commands list --available`，分类 statuses / comments 两类读取）
- JSON 解析（容忍前置进度行；截断或非 JSON 明确失败，不返回空对象）
- 响应结构校验、超时（20s）、额度不足与限流的分类
- 凭据脱敏（Bearer / token / code / client_secret / 长不透明串）
- **命令注入防护**：`execFile(BINARY, argvArray)`，可执行文件名写死 `'weibo-cli'`，
  全程 `shell` 未启用，参数以数组展开，不 join、不拼接

### 需要主人自行完成的官方步骤

官方手册（<https://open.weibo.com/cli/quickstart>）要求按顺序完成，插件不能代替：

1. 安装：`npm install -g @weibo-ai/weibo-cli`（需 Node.js 18+）
2. 在微博客户端扫描二维码完成**开发者认证**（扫脸）
3. 在控制台「我的服务」**领取体验服务**（7 天，每账号一次）或**购买积分包**（¥69 起）
4. `weibo-cli auth login` 完成 OAuth 登录
5. `weibo-cli doctor` 确认状态就绪

**这些步骤我没有执行，也不应该执行**：它们涉及账号登录与付费。

### 本轮范围

按任务书：URL → 正文 → 评论 → ConversationGraph → 分析 → 生成候选。**不开放微博真实
自动发表。**

**结论：适配层已通过（代码与测试），真实读取未验证。**

## 五、贴吧业务闭环

### 已完成（有测试）

1. 提交真实帖子链接 → 2. 读取帖子 → 3. 识别主人账号 → 4. 读取争论链 →
5. 标明缺失楼中楼 → 6. 生成候选 → 7. 显示安全审查 → 8. 在 DSH 中审核

这条链路在**假适配器 + 夹具**上全部通过（贴吧原有回归测试 830 → 840 项全绿的部分）。

### 未完成

**真实已登录账号的受控发表与回读，本轮没有执行。**

原因：本机 IP 对贴吧持续 403（拦截页，非登录态问题），没有可用的贴吧会话。这不是代码
问题，是网络可达性问题。

按任务书要求设计好的受控验收流程（供有权限时执行）：

1. 主人提供**测试站点/测试帖**（不是公开争论帖，避免影响真实用户）
2. 主人明确指定：测试账号、发表位置、正文
3. 插件读取 → 生成候选 → 主人在 DSH 里逐字审核
4. 主人点「批准这一条」（走 `/approve` 真实路由，不是工具参数）
5. 发表一次；**不把 HTTP 200 当成功**——必须回读核对正文与作者
6. 保留去重与批准记录；结果不明时**不自动重发**

**结论：只读分析链路已通过（模拟），真实发表未验证。**

## 六、争论理解：路人参与

### 缺的是什么

任务书列的九项输出，`DebateBrief` 早有八项。缺「哪些评论是路人参与」——原因在数据源：
`Dispute.exchange` 刻意只保留两人。

### 修复后

| 项 | 状态 |
| --- | --- |
| `Dispute.bystanders` 收集同层第三方 | ✅ |
| 按发言次数排序 | ✅ |
| 不混入主人/对手 | ✅ |
| 无第三方时为空数组（不是 `undefined`） | ✅ |
| `DebateBrief.bystanders` 区分「未收集」与「没人」 | ✅ |
| `renderBrief` 独立小节 + 「不要当成对手」说明 | ✅ |

最后一条是防灌水：把对手自己的帖子算成「有路人支持他」，会让支持人数虚高。

## 十、子智能体工作报告

**本轮没有使用子智能体。**

任务书建议的委派项里，辅助任务 B（微博 ID 样例测试、ConversationGraph 引用测试、
README 状态更新）看起来可以拆，但实际都依赖同一个前提：**先确定分段算法对不对**。

我在这上面花的时间说明了原因：三组样例里有一组不自洽，必须手算复核、反推分组、判断
是「样例错」还是「算法错」。这个判断一旦交给子智能体，它要么照抄样例写了个红测试，
要么改算法去迁就错的样例——两种结果都比我自己算更糟。

README 的状态更新同样需要与 provider 的 `unverified` 改动逐字对齐，拆出去会产生两份
不一致的措辞。

下一轮如果有真正独立的批量任务（例如为 20 个历史测试文件补注释、或独立的文档校对），
我会并行委派。
