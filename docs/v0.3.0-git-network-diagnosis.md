# Git HTTPS 故障诊断与修复（2026-11-10）

> 结论先行：**GitHub 没有不通。** 通的是 GitHub API，断的是本机到 `github.com:443`
> 的那条 Git HTTPS 通道；换一个本机代理端口后 `git ls-remote` / `fetch` / `push` 全部恢复。
>
> 本文只记录事实与可复现的步骤，不含任何 Token、Cookie 或私钥。

---

## 一、执行环境

| 项 | 值 |
| --- | --- |
| Windows 身份 | `win-v3kn8ar0qnq\tymo001`，`USERPROFILE=C:\Users\TYMO001` |
| 与用户主机 | **同一个 Windows 身份、同一份 `~/.config/gh` 凭据**（不是独立容器） |
| Git | `2.56.0.windows.4`，`http.sslbackend=schannel` |
| gh | `C:\Program Files\GitHub CLI\gh.exe`，登录 `alicia1030su` |
| 仓库权限 | `admin: true`、`push: true` |
| 环境变量覆盖 | `GH_TOKEN` / `GITHUB_TOKEN` / `GH_CONFIG_DIR` / `GH_HOST` 均未设置 |

## 二、症状与分层结论

| 通道 | 结果 |
| --- | --- |
| `gh api user` / `gh api repos/...` | **正常**（HTTP 200） |
| `api.github.com:443`（直连与经代理） | **正常** |
| `github.com:443` 直连 | TCP 连接超时（约 21 秒） |
| `github.com:443` 经环境代理 `127.0.0.1:58088` | TLS 被重置（`schannel: server closed abruptly`） |
| `github.com:443` 经系统代理 `127.0.0.1:10001` | **正常**（HTTP 200，约 1.3 秒） |
| `git ls-remote` 默认（走 58088） | `CONNECT tunnel failed, response 502` |
| `git ls-remote` 禁用代理 | `Failed to connect to github.com:443 after 21057 ms` |

**根因不是 GitHub 故障，也不是证书问题**：同一台机器上 `api.github.com` 一直可用，
`github.com` 只是被当前会话注入的代理（`HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:58088`）
拒绝或中断；直连又被网络侧阻断。系统代理 `127.0.0.1:10001` 可以正常隧道到 `github.com`。

## 三、修复方式（只改仓库级配置）

```bash
git config --local http.proxy http://127.0.0.1:10001
git config --local http.version HTTP/1.1
```

- **没有**改全局/系统配置；
- **没有**关闭 SSL 校验（`http.sslVerify` 未动）；
- **没有**重新登录，也没有写入任何 Token；
- 代理端口是**本机**事实，换一台机器需要重新确认（先用 `curl -x` 试通再写配置）。

## 四、验证（真实 Git 协议，不只是 API）

| 步骤 | 结果 |
| --- | --- |
| `git ls-remote origin refs/heads/main` | `476bd7db618b8d9d21187fe3534bcb54d0ce031a` |
| `git fetch origin main` | `ebfebff..476bd7d  main -> origin/main` |
| `git push --dry-run origin HEAD:refs/heads/tmp/connectivity-check` | `* [new branch]`（未真正创建，事后确认远端无此分支） |
| 真实 `git push origin release/v0.3.0-ship-authorization` | `44d702f..94f0efa` 成功 |

## 五、SSH 与 API 兜底

- `github.com:22` 与 `ssh.github.com:443` 的 TCP 可连，`ssh.github.com:443` 能读到 SSH banner；
- 但 `~/.ssh` 里只有 `known_hosts`，**没有私钥**，所以本轮不走 SSH，也没有生成新密钥；
- `scripts/push-via-api.mjs` 仍然保留为兜底：它按 tree 校验、非强制更新、父提交必须对上远端 HEAD。
  本轮不需要它，但它是 Git 通道再次中断时的安全退路；
- `ship.mjs` 的推送阶段用 `git push`，仓库级代理对它同样生效，因此**没有修改 ship.mjs**，
  也就没有新增一个敏感 PR。

## 六、边界

- 这个修复只对**当前仓库**生效；新克隆的仓库需要重新设置。
- 若 `127.0.0.1:10001` 不再监听，先用 `curl -x` 找可用端口，再改配置。
- 本轮没有验证 SSH 推送，因为不存在可用密钥；也没有为了让 SSH 能用而生成密钥。
