## 三、§三 DebateBrief 误判矛盾（P1）

### 复现

主人「我喜欢吃苹果，尤其是红富士苹果。」／对方「我喜欢喝乌龙茶，尤其是热乌龙茶。」

- v0.2.12 输出：`…两者不能同时成立。`
- `validateBrief()` 返回：**零问题**

后者说明现有校验只检查引用存在与身份归属，不能证明语义结论正确——任务书的判断成立。

### 修法

新增 `src/conflict.ts`，五种关系，只有 `contradiction` 产生分歧条目。

实现中修掉**三个自身缺陷**：

1. **极性不能只看否定词**。「12 万不算贵」与「12 万太贵了，不值」都含「不」，被判为「同极性 → 共同前提」。改用极性词。
2. **肯定词是否定词前缀**。`可行` 是 `不可行` 的子串，正负同时命中 → `undefined` → 清晰对立变 `unknown`。改为否定优先。
3. **相同数字不等于共识**。一方陈述「12 万」、另一方评价「12 万不算贵」时，原逻辑判 `shared_ground`，掩盖了真实分歧。改为仅在语域相同时才判共同前提。

连带修正：

- `extractClaims` 丢疑问句，把对手的完整质疑削成「有数据吗」，判定器看不到共同主题。立场摘要改取第一条实质发言原文。
- `validateBrief` 原本强制要求至少一条分歧，与「无法证明就不输出」直接冲突。改为允许无分歧，但**必须说明原因**。

### 验证

`test/v0213-conflict-semantics.test.ts`（14 项）。六组**独立标注预期**的用例（`expect` 字段先写人判断，再与代码输出比对），覆盖任务书 §三 列出的全部八种情形。

其中「对手提问后主人回复了无关内容」一例，**如实标注为已知局限**：现有启发式把「今天天气不错」当作实质回复，因而认为问题已被回答。测试文档写明这是 observed behaviour with a documented gap，不是正确行为——回答得好不好需要语义匹配，本版没有。

## 四、§四 微博诊断接入设置页面（P1）

### 复现

`src/platforms/weibo/diagnostics.ts`（277 行）与 `Provider.describeDiagnostics()` 都在，但 `src/settings-routes.ts` 里 **`describeDiagnostics` / `weibo` 零命中**。审计结论「没有发现设置页面真正调用该诊断的正式链路」成立。

### 修法

| 层 | 改动 |
| --- | --- |
| Host 接口 | `SettingsRouteDeps.platformDiagnostics?(options)` |
| Host 路由 | `GET /status` 附带 `platforms`；`POST /action {refresh-platforms}` |
| Host 装配 | `src/index.ts` 遍历 `platforms.list()`，按成员存在性探测，不 switch on id |
| Client 状态 | `store.platformBlocks` + `store.refreshPlatforms()` |
| Client 渲染 | `PlatformLiveBlock` 组件 + `liveEntryFor` 按 id 配对 |

十项要求逐条：

| 要求 | 实现 |
| --- | --- |
| ①已认证的查询 | 走同一个 `guard`（loopback + Origin + DSH 会话） |
| ②正式调用动态诊断 | `adapter.describeDiagnostics()`，非清单推测 |
| ③安全传给 Client | 只传状态枚举/版本/命令名/失败原因，无 cookie/token |
| ④平台→微博区域加诊断与刷新按钮 | `PlatformLiveBlock` 的 `platformLiveRefresh` |
| ⑤客户端不丢弃新字段 | 遍历 `state.lines` 逐条渲染 `message`，不 switch 固定键 |
| ⑥显示真实 CLI 状态 | 来自 `readiness.status`，非 manifest |
| ⑦失败时显示原因 | `entry.error` 渲染为「诊断读取失败：…」 |
| ⑧未检测到的不显示成已通过 | `not_implemented` → 「未知」灰标 |
| ⑨不显示 Token/Cookie | 适配器输出里没有，路由也不会补 |
| ⑩未认证读不到 | 测试断言 401 且响应不含诊断内容 |

## 五、§五 真实微博 CLI 命令语法（P0）

### 方法

本机 `weibo-cli`、`npm` 均不存在，`commands list/show` 无法执行。改为从 npm registry 下载官方包 **`@weibo-ai/weibo-cli@0.9.8`**（当前 latest），**只读**解包到临时目录核对 `dist/main.js`、`dist/args.js`、`dist/help.js`，用完删除。

### 三条 P0：假设全部与官方相反

| # | v0.2.12 的假设 | 官方实际（`main.js`） | 后果 |
| --- | --- | --- | --- |
| 1 | `commands show <name>` | `const group = rest[0]; const action = rest[1]; if (!group \|\| !action) throw new Error('Usage: weibo-cli commands show <group> <action>')` | **每次必抛** |
| 2 | 目录行有 `name`/`command`/`path` | 只有 `cmd.group` 与 `cmd.action` | **目录恒为空** |
| 3 | 帖子 id 走位置参数 | `handleInvoke = async (group, action, flags)`，调用 `handleInvoke(command, subcommand, flags)` —— **签名无 `rest`** | 位置参数**静默丢弃** |

第 3 条最危险：CLI 不报错，看起来成功，实际请求不带 id。

### 修法

- `WeiboCliCommand` → `{group, action, name, access?, flags?}`
- `inspectCommand` / `runReadCommand` 接受命令对，argv 为 `[group, action, ...flags]`
- 参数列表从 `flags` 读（官方 payload 就在这里）
- `--page` / `--count` 仅在命令声明该 flag 时发送（官方 `assertKnownFlags` 对未声明 flag 是硬错误）
- 错误体（stderr 的 JSON 信封）先读 `code`，补 11 个错误码映射，正则退回兜底

### 验证

`test/v0213-cli-compat.test.ts`（9 项）。断言的是**真正 spawn 出去的 argv**，不是内部状态——因为 v0.2.12 的测试正是在假 CLI 上「通过」的：假 CLI 是我写的，语法也是我写的，两者当然一致。
