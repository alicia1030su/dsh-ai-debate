## 一、扫描结果不再泄露凭据原文

### 1.1 原来的问题

两个扫描器在命中后都把整行放进 `sample`：

```js
findings.push({ path, label, sample: line.trim().slice(0, 120) })
```

然后分别进入：

- `source-zip.mjs` 抛出的 `Error` message → stderr → CI 日志；
- `scan-archive.mjs` 的终端输出与 `--json` 产物 → 日志、issue、工单。

于是「发现泄露」这一步自己完成了第二次泄露。CI 日志是公开的，`--json` 会被贴进 issue，
异常栈会被上传到各种收集器 —— 一条真的 Cookie 被抓到之后，最不该做的事就是再把它写出来。

### 1.2 现在的输出

新增 `scripts/lib/scan-finding.mjs`，命中的形状被固定为：

| 字段 | 含义 |
| --- | --- |
| `path` | 归档内路径 |
| `rule` | 规则名（如 `AWS access key id`） |
| `kind` | `content` / `name` / `type` |
| `line` + `column` | 文本文件的位置（1 起） |
| `offset` | 二进制文件的字节偏移 |

构造函数**不接受内容参数**，所以调用方没有「顺手把匹配串带出去」的通道。文本模式打印
`path:line:column — rule`；JSON 模式输出同样的字段。

不输出：命中子串、前后缀、整行、命中长度。前缀也不行 —— 一把钥匙的前 4 个字符仍然是
钥匙材料，长度也能缩小猜测范围。

### 1.3 顺带修掉的二进制盲区

原来 `if (raw.includes(0)) continue` / `entry.data.includes(0) continue`：二进制文件
直接跳过。但模式都是 ASCII，一张 PNG 的元数据里同样可以藏一个令牌。现在二进制走同一条
扫描，位置用字节偏移表示。真实仓库的 20 个 PNG 没有命中，这一条是覆盖率提升，不是噪音。

### 1.4 负向测试

`test/v0239-scan-safety.test.ts`（19 条）。对**旧实现**运行，17 条红：

```
not ok 1  扫描器：命中凭据时退出非零，但 stdout / stderr / JSON 都不含凭据原文
not ok 2  扫描器：JSON 结构里没有 sample / 命中内容字段
not ok 3  扫描器：二进制文件里的凭据同样被发现，且输出不含原文
not ok 4  打包器：命中凭据时异常信息里没有原文，但有文件与行号
...
```

断言是逐字节的：注入 `AKIA…`（测试内拼出来，文件字节里不存在连续模式），运行扫描器，
把 stdout、stderr、JSON 拼起来，要求：

- 不出现凭据原文；
- 不出现凭据前 8 位；
- 仍然出现文件路径、规则名、行号。

打包器那条同样检查 stderr。

## 二、不可解析的归档条目不再被跳过

### 2.1 原来的问题

`scan-archive.mjs` 的 ZIP 读取器按签名在整份字节里扫描，遇到解压失败就：

```js
try { data = method === 0 ? payload : inflateRawSync(payload) } catch { data = undefined }
...
if (entry.data === undefined) continue
```

同一个 `continue` 覆盖了：损坏的 deflate、未实现的压缩方式、截断的数据。TGZ 读取器对
非普通条目也返回 `data: undefined`，同样被跳过。**读不出来的那一个文件，正是没有人能
担保的那一个。**

### 2.2 现在的分类

| 类别 | 判定 | 处置 |
| --- | --- | --- |
| 合法目录 | 名称以 `/` 结尾、MS-DOS 目录位、Unix `S_IFDIR` | 接受，计入 `directories`，不扫描内容 |
| 合法非普通条目 | Unix 符号链接/设备等；tar typeflag 非 `0`/`\0`/`5` | 作为**发现**报出（发布源码包没有理由带链接） |
| 正常文件 | 方法 0（stored）或 8（deflate），长度与 CRC 相符 | 扫描 |
| 压缩数据损坏 | deflate 解不开 / gzip 校验失败 / tar 头校验失败 | `[corrupt]`，exit 3 |
| 不支持的压缩方式 | ZIP method ∉ {0, 8}、加密、ZIP64、分卷 | `[unsupported]`，exit 3 |
| 长度或偏移异常 | 本地头/数据越过中央目录、解压长度与声明不符、CRC 不符、EOCD 偏移越界 | `[bounds]`，exit 3 |
| 归档截断 | 找不到 EOCD、条目数据不足、tar 缺结束块 | `[truncated]`，exit 3 |

ZIP 改为通过**中央目录**读取，不再在整份字节里找签名。EOCD 的注释长度必须恰好消耗到
文件末尾，否则压缩数据里的巧合签名会被当成索引。TGZ 校验每个 ustar 头的校验和，并要求
两个零块结束；结束后还有非零数据也算损坏。

### 2.3 负向测试

同一文件的第 5–17 条：

- 合法目录被接受并计数（`目录 2`），不是「跳过」；
- 目录条目里的禁止路径仍然被识别为目录，不误判成环境变量文件；
- ZIP 符号链接、TGZ 符号链接作为发现报出；
- 不支持的压缩方式（method 12）→ exit 3，输出 `不支持的压缩方式 12`；
- 损坏的 deflate → exit 3，`[corrupt]`；
- CRC 不符 → exit 3；
- 解压长度与声明不符 → exit 3；
- 截断 ZIP → exit 3，`[truncated]`；
- 中央目录偏移越界 → exit 3，`[bounds]`；
- 损坏 gzip → exit 3；
- 缺 tar 结束标记 → exit 3；
- 声明大小超出归档末尾 → exit 3。

没有新增任何扫描豁免；另有两条测试直接断言脚本里不存在 `startsWith('test/')`、
`FIXTURE_MARKER`、`SCAN_EXEMPT`。

### 2.4 边界

`scripts/lib/archive-verify.mjs`（`verify-source-archive` 使用）是另一套读取器。它不做
静默跳过：inflate 失败会抛出，长度不符会在逐文件比对时判红。它没有像扫描器这样对每种
异常给出分类，本轮没有改它 —— 它不承担「扫描发布物」的职责，且失败方向是红而不是绿。

### 3.4 `approved: false`：只撤销或初始化

真实 diff 里 `src/runtime.ts` 涉及 `approved` 的只有三行：

```diff
-          ...(reaimed ? entry.candidates.map((row) => ({ ...row, approved: false })) : entry.candidates),
+              ...(reaimed ? entry.candidates.map((row) => ({ ...row, approved: false })) : entry.candidates),
+            ? entry.candidates.map((row) => ({ ...row, approved: false }))
```

第二行是同一表达式的重新缩进；第三行是新增的**撤销**分支（没有草稿且重定向时，把旧候选
全部置为未批准）。新候选的 `approved: false`（`candidateBase`）与编辑路径的撤销都不在
diff 里，未变动。

静态与行为证据：

- `src/runtime.ts` 全文 0 处 `approved: true`；
- 5 处 `approved: false` 只分「新对象初始值」与「撤销映射」两类；
- 拒绝且不重定向 → 保留旧批准、不加空候选；
- 拒绝且重定向 → 撤销旧批准、不加空候选；
- 变异验证：把 `storeCandidate` 改成恒真，两条行为测试立刻变红。

新增 `审计：授予批准只发生在三个显式操作里`：用 `git grep` 钉住
`src/import/workflow.ts`、`src/index.ts`、`src/publisher.ts` 三个文件。多出第四个，
说明有人开了新的批准入口 —— 测试会红。

## 五、仍然存在的边界

1. **扫描仍是模式匹配。** 它证明不了「没有凭据」，只能抓住已知形状。真正的保证来自
   白名单（主）与发布前的人工复核（最后一道）。
2. **压缩炸弹没有做资源上限。** 本次只保证「读不出来就失败」，没有限制解压后体积；
   一个恶意归档可以把扫描器拖到 OOM。发布物由自己的打包器生成，风险有限，但不声称免疫。
3. **`archive-verify.mjs` 与 `ci-guard.mjs` 的 ZIP 读取仍是轻量实现。** 前者失败方向
   是红；后者只做「条目在不在」的存在性检查。扫描器的严格读取是权威判定。
4. **`test/docs` 的例外仍需要人判断「这条是不是假数据」。** 代码能保证逐字、仍然存在、
   只在这个文件；不能保证人没有把真钥匙登记进来。这是敏感审核的一部分。
5. **本轮没有重跑 Desktop。** 只改了打包器、扫描器、测试与文档，页面代码未动。
