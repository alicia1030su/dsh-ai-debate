## 一、复现（先失败，再修）

每一条都先写成会失败的测试，确认它真的失败，改完再确认转绿。

### 1. 损坏的状态文件被内存副本覆盖（P0）

`test/v028-corrupt-overwrite.test.ts`。修复前的行为（审计给出、我也复现了）：

```
store 初始化 → 写一次（文件合法）→ 外部把文件改成非法 JSON
→ store.mutate()  →  返回成功
→ 磁盘上是内存副本，原始损坏字节消失
```

成因在 `src/store.ts` 的这一行：

```ts
const base = await this.readCurrentDocument().catch(() => this.data)
```

`.catch()` 吞掉了**所有**读取异常，包括 `StoreError('corrupt')`。

### 2. 存活持有者的锁被超时回收

`test/v028-lock-recovery.test.ts`。`breakStaleLock` 把存活检查放在年龄检查**之后**，
且条件里有 `owner !== process.pid`，所以「自己持有、自己超时」的锁会被自己判为可
回收。更根本的是锁里没有持有者标识，回收之后原持有者的释放会删掉别人的新锁。

### 3. 批准快照核对与写入不是原子的

`createApprovalForSettings()` 的读、判断、写分三步。中间窗口里候选被换掉，就产生
一份描述旧内容的授权记录。

### 4. 待批准列表读的是缓存

在另一个进程里生成的候选看不见；读失败与「真的没有」在页面上是同一句话。

### 5. 微博纯数字单段链接被猜成帖子

`weibo.com/1234567890` 既可能是 uid 的主页，也可能是数字 mid 的帖子。原规则
「纯数字且长度 ≥ 6 就当帖子」把主页读成了帖子。

## 四、设计取舍（为什么这样修）

**为什么读失败要变成拒绝，而不是保留缓存继续跑。**
`checkPublishPolicy` 的每条拒绝都在问账本一个问题：「这条发过了吗」「上次发表有
结论吗」「帖子额度用完没」。这些问题只有在**读得到当前文档**时才有答案。照着可能
过期的缓存放行，代价是一条撤不回的公开重复回帖；拒绝的代价只是一次可重试的失败。
两个方向不对称，所以选拒绝。

**为什么 `transact` 不直接用 `mutate` 加抛错。**
`mutate` 的回调只能返回下一份文档。想说「不」就只能抛错，而抛错会被 store 记成
一次写盘失败（`dirty`），页面于是显示「状态写不进去」——把「你看的内容过期了」
这个正常结果，渲染成了磁盘故障。`transact` 的 `abort` 是一次干净的否决。

**为什么 `pendingApprovals` 保留旧数组字段。**
v0.2.7 的页面读的是数组。直接改类型会让旧页面在失败时读到 `undefined` 然后崩在
`.length` 上。所以旧字段保留（失败时是空数组），新增 `pendingApprovalsState` 承载
读结果，新页面优先看它。

**为什么 `staleness` 会被下一次成功 refresh 清掉。**
如果一次失败就永久标记，用户修好文件后只能重启插件——「安全拒绝」变成「永久罢工」，
同样不可接受。所以它是「最近一次尝试的结果」，不是「历史上有过问题」。
