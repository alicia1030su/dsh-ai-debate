# v0.3.0-rc.1 发布操作规程（授权到位后逐条执行）

> 这份文件是**操作单**，不是发布结果。当前状态：四个敏感 PR 均无有效授权，rc 未发布。

## 0. 唯一的外部阻断

维护者本人在 #42 / #43 / #35 / #38 各提交一条 **Comment review**（GitHub 不允许自我 Approve）：

```text
ship-approval: v1
pr: <编号>
head: <该 PR 最终 40 位 SHA>
scope: <该 PR 的敏感路径，逗号分隔>
note: <写明审阅了什么>
```

四条都到位前，任何一步都不往下走。**授权不能代写**：流水线只读 `pulls/{n}/reviews`，
代码里没有任何创建 review 的调用（`test/v0300-ship-authorization.test.ts` 有断言钉住）。

## 1. 合并顺序

已实测：`#42 → #43 → #35 → #38` 链式 squash **四步全无冲突**，且合并后两边改动语义共存
（`assertSemver` 接受 rc，同时 `judgeResumeAuthorization` 存在）。
反序 `#43 → #42` 也无冲突，但按依赖走正序更清楚。

每次合并后检查：

```bash
gh pr view <n> --json state,mergedAt,mergeCommit
git fetch origin main && git log --oneline -3 origin/main
```

`#42` 合并后 `#43` 若需重建（HEAD 变化 → 旧授权失效 → 需重新授权），按普通 PR 重开，
**不强推原分支**。

## 2. 版本改动（**留在工作区，不要先提交**）

`ship.mjs` 的 `ensureBranch` 会自己 `git checkout -b release/v0.3.0-rc.1-auto origin/main`，
`commitAll` 再把**工作区里未提交的改动**提交上去。所以这里必须只在工作区改、不要 commit：

```bash
node scripts/version.mjs set 0.3.0-rc.1     # 要求 CHANGELOG 已有 ## [0.3.0-rc.1] 段落
node scripts/version.mjs check --tag v0.3.0-rc.1
node scripts/release-dry-run.mjs
git status --short                          # 应看到 package.json / README.md / CHANGELOG.md
```

若先手工 `git commit`，`commitAll` 会看到 `git status` 干净、什么都不提交，然后推一个
**空分支**上去（PR 里没有 diff）。这是本轮读代码时发现的，未在真实发布中触发过。

`version.mjs set` 会先检查 CHANGELOG 段落是否存在 —— 版本先改、说明后补会让发布说明一直是空的。
该段落已在本轮集成分支里写好（见 `docs/v0.3.0-rc-verification.md`），合并时一并带入。

产物构建（`ship.mjs` 的 verify 阶段会重做，这里只是提前确认）：

```bash
node scripts/pack.mjs && node scripts/source-zip.mjs --out .
node scripts/scan-archive.mjs dsh-ai-debate-0.3.0-rc.1.tgz
node scripts/scan-archive.mjs dsh-ai-debate-source-0.3.0-rc.1.zip
node scripts/verify-source-archive.mjs dsh-ai-debate-source-0.3.0-rc.1.zip
```

## 3. 自动交付

```bash
node scripts/ship.mjs
```

它会：编译 → 类型棘轮 → 全量测试 → 打包 → 双包扫描 → `ci-guard --require-archive` →
`version check` → 建分支 → commit → push → 开 PR（`release/v0.3.0-rc.1-auto`）→
等 CI → squash 合并 → 打 annotated tag `v0.3.0-rc.1` → 等 Release → 核验附件。

版本分支相对 main 只改 `package.json` / `README.md` / `CHANGELOG.md`，
`classifySensitive` 实测判定为**非敏感**（`{"sensitive": false, "reasons": []}`），
因此会自动合并，不会停在 PR。

**如果它停在 PR**，说明 diff 里混进了敏感路径 —— 那是真问题，要查，不要放行。

## 4. 发布后核验（必须从 GitHub 下载真实附件）

```bash
gh release download v0.3.0-rc.1 --repo alicia1030su/dsh-ai-debate -D /tmp/rc-assets
cd /tmp/rc-assets && sha256sum *          # 与 Release 正文里的哈希逐字比对
node <repo>/scripts/scan-archive.mjs dsh-ai-debate-0.3.0-rc.1.tgz
node <repo>/scripts/scan-archive.mjs dsh-ai-debate-source-0.3.0-rc.1.zip
node <repo>/scripts/verify-source-archive.mjs dsh-ai-debate-source-0.3.0-rc.1.zip
node <repo>/scripts/verify-install.mjs dsh-ai-debate-0.3.0-rc.1.tgz
gh api repos/alicia1030su/dsh-ai-debate/releases/tags/v0.3.0-rc.1 --jq '{prerelease, draft, tag_name}'
gh api repos/alicia1030su/dsh-ai-debate/releases/latest --jq .tag_name
```

三条硬判据：

1. `prerelease == true`；
2. `releases/latest` 仍是 **`v0.2.39`**（rc 不得取代 Latest）；
3. 下载文件的 SHA-256 **等于** Release 正文里印的那个 —— 不等就是失败，不是「小差异」。

### 关于本机一个已知限制

`scripts/verify-install.mjs` 在本机跑到「按声明安装依赖」时会以 127 退出：它用
`cpSync(..., { dereference: true })` 复制 pnpm 的符号链接包，而当前沙箱禁止创建符号链接
（`EPERM: operation not permitted, symlink`）。**这不是打包缺陷** —— 解包、依赖契约、
`lib/index.js` 的导入解析都在此之前通过了；CI 与 GitHub runner 不受此限制。

发布后第 4 步里的 `verify-install` 若在本机失败，要以 CI 的
`verify.mjs`（含「裸目录安装验证」）结果为准，并在报告里写明本机为什么跑不了。

## 5. 不算数的做法

- 用本地产物哈希冒充正式附件哈希（Actions 会重新打包）；
- 把 `prerelease` 缺省当成 false（GitHub 缺省就是 false，必须显式 `--prerelease`）；
- 用 `--resume` 复用旧授权（`judgeResumeAuthorization` 会用 `commit_id` 拒掉）；
- 把「工作流跑绿」当成「Release 建好」（`ship.mjs` 会真的去 `gh release view`）。
