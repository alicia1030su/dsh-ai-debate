## 一、这一版做了什么

v0.2.38 的交付报告里留了三句硬话：语义质量没有被证明、新用户旅程没人走过、源码包根因未修。
这一版处理这三条，另外补上「结果说不清」和「升级没验证」。

| 目标 | v0.2.38 的状态 | v0.2.39 的做法 |
| --- | --- | --- |
| 生成结果只有两态 | 成功 / 失败 | 五态：valid_draft / needs_more_context / unjustified_refusal / invalid_draft / technical_failure |
| 空白候选 | 导入链路已修，真实平台链路漏了 | 两条链路按结果类型分流，拒绝与故障都不落候选 |
| 质量结论 | 只有代理指标，无盲评 | 三版同条件生成 + 随机打乱隐藏版本 + 两个自动评审来源 |
| 源码包根因 | 加了漂移检查，但根因还在 | 全部字节来自 `git cat-file`，工作树行尾不再影响产物 |
| fixture 冲突 | 两个刻意入库的假 CLI 进不了包 | 精确路径例外收录，不放开任何其他 node_modules |
| 首次使用 | 无引导，错误提示是「调用失败」 | 三步清单 + 十二类错误的可执行下一步 |
| 升级 | 只在报告里推测兼容 | v0.2.37 / v0.2.38 的 store 与配置逐键测试 + 故障注入 |

## 二、生成结果：从两态到五态

### 2.1 为什么必须拆

两态（成功/失败）把四种不同的事实在数据上压成一种：

| 结果 | 含义 | 旧表现 |
| --- | --- | --- |
| `valid_draft` | 有正文、无硬违规、目标对得上 | 成功 |
| `needs_more_context` | 材料确实不够，模型追问 | 记成失败 |
| `unjustified_refusal` | 材料够，模型仍拒绝 | 与上一条混在一起 |
| `invalid_draft` | 有正文但违反事实/目标/安全 | 失败 |
| `technical_failure` | 超时、截断、解析失败 | 失败 |

后果是可验证的：两版的「失败率」可以完全相同，而一版是拒绝得对、另一版是编造得多。
在这种口径下，「这一版比上一版好吗」在数据上无法回答。

### 2.2 判据，以及它为什么是保守的

新增 `src/outcome.ts`。判「该不该拒绝」只用一条：简报里有没有可打的论据
（对方论据数 / 未答问题数 / 目标是否确认）。

方向是**故意保守**的：判「材料够」而模型拒绝 → 记缺陷；判「材料不够」而拒绝 → 记正确。
宽松判据会把大量合理拒绝记成缺陷，于是这个指标再也说明不了问题。

### 2.3 `forceAttempt`：把最终判断交回给模型

第一次真实采集暴露了一个真问题：q06（对方只说「方案我贴了」）与 q19（对方只说「还是没证据」）
被判成 `unjustified_refusal`，而模型的拒绝理由完全站得住 —— 那两条「论据」只有指路，没有内容。

计数规则看不出这个区别。所以加了一条开关：**用户从页面点「生成候选回复」时**
（`forceAttempt: true`），模型说材料不足就记为 `needs_more_context`；没有用户表态的
自动链路仍然保守判缺陷。

这不是放宽标准，是承认「谁在做决定」：用户已经明确要求试一次，此时由模型给出具体缺口
比由计数规则替他决定更合适。安全边界没动 —— 拒绝仍不落候选，违规仍被拦下，目标仍要校验。

### 2.4 空候选：两条链路都修了

v0.2.38 只修了导入链路，真实平台链路仍会在 `needs_more_context` 时落一条 `text: ""` 的候选。
现在两条链路都按 `outcome` 分流：只有 `valid_draft` / `invalid_draft` 写候选。

页面对三种「没有候选」给三种说法：补材料（不着红）、换模型/换打法（标红）、重试（标红）。
`invalid_draft` 有正文但没过检查，页面上已有违规清单，不重复提示。

### 2.5 一次真实的数据失真，以及它教的事

改完之后第一次采集，19 条拒绝全被记成 `technical_failure`。逐层查下来：

- 分类器对；
- `generateForImport` 把 `outcome` 放进了返回值；
- **`index.ts` 把 `StepResult` 映射成页面响应时只搬了 `reason` 和 `next`**；
- 采集器看到没有 `outcome`，按「没有类型就是故障」处理。

中间任何一跳漏搬一个字段，下游看到的就只有「成功/失败」—— 而它不会报错。
现在有一条测试专门数「两条返回路径是否都搬了 `outcome`」（`v0239-outcome-plumbing.test.ts`）。

## 三、真实模型盲评

### 3.1 条件

| 项 | 值 |
| --- | --- |
| 案例 | 20 个脱敏案例（与 v0.2.38 同一批，`q01`–`q20`） |
| 版本 | v0.2.37 / v0.2.38 / v0.2.39 |
| 模型 | 宿主 `host-llm`（三版同一条路径、同一默认模型） |
| 人格 | `tieba_veteran`（三版固定） |
| 打法 | 自动选择（三版各自选，记录在选择结果里） |
| 生成参数 | temperature / maxTokens 同期同值 |
| 预算 | 每版 20 次调用，硬上限 22 |

v0.2.39 当轮的结果分布：`valid_draft` 19、`technical_failure` 1（q07 连续两次被截断）。
策略分布：`answer_core` 15、`demand_basis` 2、`ask_clarification` 2。
安全结论：`allow` 17、`review` 2、无结论 1（那条就是被截断的）。

### 3.2 盲评怎么做的

`scripts/blind-review.mjs`：

1. 三版输出按案例汇总，**每个案例内部用固定种子的伪随机打乱**（`0x20390001`，写进结果文件）；
2. 匿名标签 `R001…R060`，版本映射单独写进 `key.json`；
3. 评分过程只读 `bundle.json`（不含版本），解盲是之后单独一步（`blind-summary.mjs`）。

打乱用固定种子而不是 `Math.random()`：同一条命令跑两次要得到同一顺序，否则「随机打乱」
这句话无法被第三方复核 —— 而不可复核的随机化，与「挑好看的」在结果上无法区分。

### 3.3 评审来源：两个，都是自动的

| 来源 | 量什么 | 明确不是什么 |
| --- | --- | --- |
| `rules` | 空不空、字数、数字能否追回原文、有没有对人说话 | 不是语义判断 |
| `structure` | 跨案例三字片段重复率、最常见开头 | 不是「论证好不好」 |

**没有人工评审，也没有模型评审。** 拿不到真人就写拿不到 —— 把「一个规则算的」写成
「独立评审」，是这个项目里最容易犯也最难被发现的一类失真。

### 3.4 结果（三版解盲后）

| 指标 | v0.2.37 | v0.2.38 | v0.2.39 |
| --- | --- | --- | --- |
| 产出正文 | 20/20 | 19/20 | 19/20 |
| 空白回复 | 0 | 1 | 1 |
| 平均字数 | 50.9 | 46.4 | 49.5 |
| 每百字命中具体要素 | 5.41 | 4.31 | 3.74 |
| 不可追溯数字 | **0** | **0** | **0** |
| 对人说话 | 12 | 15 | 12 |
| 跨案例共享三字片段 | 2.8% | 2.7% | 2.0% |

> 完整分解、每个指标的局限、以及「为什么不能用它下结论」，写在
> `docs/v0.2.39-blind-review.md`。

### 3.5 结论：没有测出「新版更好」

三次采集（不同构建）的解盲结果都指向同一件事：

- **命中具体要素没有提升**。这个指标奖励复述原文、惩罚改写，与「论证是否切中要害」不是一回事。
- **不可追溯数字始终为 0**（三版都是）。这是唯一一条三版都稳定通过的硬指标。
- **共享片段率下降**（2.8% / 2.7% → 1.3%），说明模板感在减弱 —— 但这是三条回复样本上的
  一个辅助量，不足以支撑「表达质量提升」。
- **问句密度**：v0.2.37 1.28/百字、v0.2.38 2.16、v0.2.39 1.50。三版都在追问，只是多少不同。

**唯一有实证证据的改进是「结果可分辨」**：这一版能说清每条产出属于五态中的哪一种，
并能统计「该拒绝的拒绝了几次」。v0.2.37 与 v0.2.38 做不到 —— 它们只有一个「失败」桶。

不给提升百分比。20 案例、单次采样、非盲人评审，任何百分比都会读起来比它实际能支撑的更强。

## 四、源码包：字节只由提交决定

### 4.1 根因与修法

v0.2.38 的诊断是「工作树行尾会污染源码包」，处置是加一个打包前的漂移检查。检查能发现脏
工作树，但不能阻止在脏工作树里打包 —— 而发布不应当依赖「有人记得先跑另一个命令」。

v0.2.39 把读取路径换掉：

- 清单用 `git ls-tree -r --full-tree <commit>`（不是 `ls-files`：索引里暂存未提交的改动不算发布内容）；
- 内容用 `git cat-file --batch` 一次读全部（几百个文件不 fork 几百次）；
- **发布模式要求 Git**：`--rev` 解析不到提交、或目录里根本没有 Git，都直接失败且不写文件
  （v0.2.39 复审 §1；无 Git 回退改为显式 `--allow-working-tree`，且不得与 `--rev` 同用）；
- `--rev` 可打任意提交的包。

新增 `scripts/lib/git-objects.mjs`：按字节偏移切 `cat-file --batch` 的输出流。按字符串截断
会切坏 UTF-8 中文，所以这里必须按 Buffer 切。

### 4.2 验收：同一提交，两种工作树，同一串字节

| 场景 | 工作树状态 | 结果 |
| --- | --- | --- |
| A | LF，无未跟踪文件 | 基准 |
| B | **648 个文本文件被改写成 CRLF**，并有未跟踪文件 | 与 A **逐字节相同** |

同一提交、两处工作树、其中一处被整体改成 CRLF —— 产物字节完全一致。这条验收现在是
`test/v0239-source-archive-authority.test.ts` 里的自动化用例，不需要手工复现。
（文件数会随仓库增长变化；结论是「相同」，不是某个具体计数。）

### 4.3 fixture 冲突（§5.2）

`.gitignore` 自 v0.2.33 起为 `test/fixtures/fake-weibo-pkg/node_modules/**` 开例外（那是刻意
入库的假微博 CLI，桌面验收要靠它解析入口）。但打包器的 `FORBIDDEN_DIRS` 无条件排除
`node_modules`，于是那两个文件**永远进不了源码包** —— 而源码包正是下载者用来复现验收的东西。

修法是**精确路径例外**（`TRACKED_FIXTURE_EXCEPTIONS`，两条完整路径）：

- 不放开任何其他 `node_modules`；
- 例外仍要通过全部文件名检查（`.env` / 密钥 / 归档后缀仍然拒绝）；
- 例外必须在提交里真实存在（`contents` 由对象库填充，缺了会在最终闸门报错）。

测试钉住两件事：假 CLI 在包里、`node_modules/left-pad` 这类真实依赖目录不在包里。

### 4.4 可复现的边界

- 同一提交 → 同一串字节：**成立**（上面 A/B 实测）。
- 跨平台（Linux runner vs Windows）：**未验证**。zlib 的压缩实现与 gzip 头 OS 字段都可能不同；
  `pack.mjs` 的 tgz 已经把 OS 字段钉成 255，源码 zip 用的是 `deflateRawSync` 的默认参数，
  没有做过跨平台对照。**不声称全平台一致。**

### 4.5 内容扫描：从「按目录豁免」改为「按字节登记」（复审 §2）

原来的扫描有三层豁免：一份按文件名的豁免表、一个「行里出现 fixture 关键字就跳过」的正则、
以及 `test/`、`docs/` 的整目录跳过。三者都不可验证 —— 把一把真 AWS key 粘进任何测试文件，
构建仍然是绿的。

现在例外只剩一种形态：**某个路径里的某一串确切的假值**（`scripts/lib/fixture-allowlist.mjs`，
7 条、5 个文件）。同文件里换一把钥匙、别处新增一把，都会让构建失败。私钥登记的是整行而不是
头一行 —— 头一行在真钥匙里长得一模一样。

独立扫描器 `scan-archive.mjs` 用同一份数据，但保留自己的模式表与判定流程：共用的是「哪些字节
被认定为假数据」这个事实，不是同一个扫描实现。

## 五、首次使用

### 5.1 三步清单

离线导入面板最上面加了三步：配模型 → 粘讨论 → 预览+分析+生成。它只陈述顺序，不假装知道
用户配没配模型（那需要一次探测），所以措辞是「第一次用，按这三步走」。

### 5.2 十二类错误的可执行下一步

新增 `src/guide.ts`。每类错误有：一句人话、按顺序的下一步、是否可重试。

| id | 用户看到的第一句 |
| --- | --- |
| `no_host_model` | 没有找到可用的模型：这个 DSH 没有把模型服务交给插件 |
| `host_model_unavailable` | 宿主有模型服务，但没有可用模型（通常是没登录或没配密钥） |
| `bad_base_url` | 模型接口地址看起来不对 |
| `auth_failed` | 模型接口拒绝了这次请求：密钥无效、过期，或没有这个模型的权限 |
| `protocol_mismatch` | 接口回的话不是本插件认识的格式 |
| `import_format` | 这段文字没有被解析成讨论 |
| `no_comments` | 这段讨论里没有别的评论，只有原帖 |
| `insufficient_evidence` | 材料不足以支撑一条有依据的回复（这是正确行为） |
| `network` | 连不上模型服务 |
| `timeout` | 模型在规定时间内没有返回 |
| `clipboard_blocked` | 浏览器没有允许写剪贴板 |
| `quota` | 模型服务说额度用完了，或被限流 |

两条测试钉住：每条下一步都必须指向具体动作（不是「请检查配置」），标题互不重复，
可重试与不可重试分开（认证失败不该鼓励反复点按钮）。

### 5.3 数据目录说明

诊断面板加了「这个路径由谁决定」与一句说明：换 profile 时历史会话没有消失，只是这个
profile 指向另一个目录；插件**不会**扫描其他 profile 的会话。

## 六、升级与数据保护

上下文、绑定），v0.2.38 的 `defaultStrategy` 可读，未知键被忽略，值形状错了落回默认值，

（有）都能读；旧 `approved: true` 读出来仍在；**新候选不会继承旧批准**（新写入的 `approved: false`）。

### 6.3 故障注入（隔离副本）

| 场景 | 行为 |
| --- | --- |
| 写盘中途截断 | 拒绝启动，原文件原样保留（不覆盖成空状态） |
| 残留 `state.json.tmp` | 正常启动，会话可读 |
| 备份恢复 | 换回好文件后正常读取 |
| store `version: 2` | 拒绝启动并说明「备份后手动处理」，不静默降级 |

**没有**在正式用户目录上做故障注入。全部在 `mkdtemp` 出来的临时目录里。

### 6.4 未做

`store` schema **没有**升级到 v2。当前没有真实的格式变更需求，为了版本号好看而迁一次，
只会给用户多一个失败面。将来需要迁移时的机制（备份 → 验证 → 失败回滚）写在就绪报告里。

## 八、尚未验证 / 已知限制

1. **人工盲评没有做。** 两个评审来源都是自动规则。语义质量（「论证是否切中要害」）这张表答不了。
2. **跨平台字节复现没有验证。** 同平台同提交成立；Linux runner 上没做过对照。
3. **真实平台读写仍是 0 / 0。** 本轮没有做任何真实微博读取；离线草稿是唯一可用能力。
4. **新用户旅程是自动驱动的，不是陌生人走的。** 全流程由脚本在隔离 profile 上跑通，
   有人看过截图，但没有外部测试者走一遍。
5. **`source-zip.mjs` 属敏感路径。** 本版改动了它（§4.1/§4.3/§4.5），PR 必须停在维护者
   审核，不得自动合并。复审细节见 `docs/v0.2.39-review-fixes.md`。
6. **宿主 Node 出网仍未观测。** 边界结论与 v0.2.36 相同：插件出口可强制拦截，宿主进程
   Node 侧只有观测能力。
